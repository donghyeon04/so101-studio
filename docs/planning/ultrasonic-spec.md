- **2026-11-14 성능 저하**: 로보나인 + 짧은 브래킷(결정 0063)으로 센서가 작업대 위 약 154.5mm(전 설계 110mm)가 되어 같은 빔 반각에서 바닥의 빔이 넓어졌다. 벤치마크 `single` 비관 성공 78% → 62%, 3개 인식 기준을 130초로 완화했다. 빔 반각은 B1 실측 전 가정값이라, B1 뒤 다시 낸다. CHECK 높이·경로를 새 높이에 맞춰 다시 고르는 것은 초음파 세션 일이다(시험장 M6에서도 본다). 이 표의 숫자는 결정 0037대로 벤치마크 고정 시나리오와 커밋을 출처로 적는다.

"성공"은 위치 오차 15mm 이내이면서 방향이 맞은 물체 수다(정사각형 물체는 위치만). 1절의 가상 값은 2026-11-06 공식 표다. 앞 표(835a180, 평균 63~65초)보다 시간이 약 25초 긴 것은 가상 팔이 실제 팔 궤적 코드를 쓰게 되어서다: 접선·구심 가속을 함께 `tool_a_max`/√2(약 85mm/s²)로 묶고, 모서리를 2.5mm로 깎아 천천히 지나며, 180° 되돌아감에서 선다. 경로 길이와 횟수는 같고 평균 속도만 65→43mm/s로 떨어졌다. 성공률과 정확도는 씨앗 잡음(약 ±5%p) 안에서 같다. B1·B2 실측이 들어오면 벤치마크 모델 값을 고쳐 다시 낸다(결정 0037). T8은 비관에서 −7~+3%p로 이득이 일관되지 않아 기본 끔을 유지하고 U9에서 비교한다. "인식 시간"은 레이더와 팔 확인 시간의 합이고, 팔이 집고 놓는 시간은 뺀다.

## 2. 전체 흐름
```
 IDLE ─▶ PREPARE ─▶ SCAN ─▶ DECIDE ─후보 있음─▶ CHECK ─확정─▶ PICK ─▶ PLACE ─┐
    (radar_clear)   (레이더)    │                  │                        │
                                │                  └─확인 실패─▶ DECIDE      │
                                └─후보 없음─▶ RESCAN ─후보 있음─▶ DECIDE    │
                                              └─또 없음─▶ DONE              │
                     SCAN ◀──── (놓는 동안 레이더가 미리 돌려 둔 결과) ◀──────┘
```
- `SCAN`: 레이더가 후보 목록을 낸다. 후보는 `angle_deg=None`, `confidence` 0.3 이하인 `DetectedObject`다.
- `DECIDE`: 기존 규칙(도달 범위 안, 팔에서 가까운 순)으로 후보 하나를 고른다.
- `RESCAN`(새 상태): 후보가 없으면 바로 끝내지 않고, 팔을 레이더 시야를 가리지 않는 대기 자세 `radar_clear`(`PREPARE`와 같은 자세, 결정 0039: 링크 점이 모두 작업대 y 120mm 이하, 손끝 높이 150mm 이상. 기본값은 결정 0041의 위로 세운 자세 `[0, -90, 85, -90, 0, 3]`, 손끝 (300, 95.8) 높이 약 321mm)로 옮긴 뒤 레이더를 4바퀴 돌려 한 번 더 찾는다. 팔이 시야를 가려 남은 물체를 놓치는 경우를 막는다. 후보가 없을 때마다 한 번씩 하고, 연달아 두 번은 하지 않는다. 설정 `radar.rescan_home`(기본 켬). 근거: 8.5절 벤치마크(커밋 2078533, 씨앗 20개)에서 성공 +4~9%p, 인식 시간 +7~10초.
- `CHECK`(새 상태): 팔이 후보 위를 지나가며 손목 센서로 재서 중심·방향·크기를 확정한다(6절). 물체가 없으면 그 후보를 지우고 `DECIDE`로 돌아간다.
- `PICK`·`PLACE`: 그대로. `PLACE` 동안 레이더가 다음 후보를 미리 찾아 둔다(4절 T5). 그래서 두 번째 물체부터는 `SCAN`이 기다리지 않는다.
- **`radar_clear`를 거치는 때 (2026-11-06)**: 작업 실행의 첫 사이클(`IDLE → PREPARE`), `RESCAN`, 집기 실패 뒤 `PREPARE`뿐이다. `PLACE` 뒤에는 `PREPARE`를 거치지 않고 미리 돌린 결과로 바로 `SCAN`한다. 사이클마다 위로 올라갔다 내려오는 이동(약 270mm × 2)이 없어진다. 벤치마크(demo 씨앗 20, `radar_clear` [0,-90,85,-90,0,3])에서 PLACE 뒤에도 거치게 하면 낙관 100→98%, 비관 78→72%로 나아지지 않았다(씨앗 잡음 ±5%p 끝). 벤치마크도 같은 흐름으로 잰다: 첫 `SCAN` 전과 `RESCAN` 때만 `radar_clear`로 가고, 올라가는 이동은 인식 시간 밖, 내려오는 이동은 안에 넣는다.
- 다른 인식 방식(`ManualSource`, 카메라)은 `CHECK`를 건너뛴다. 인식 방식이 확인 기능을 가졌는지로 정한다(8.2절).

시간 흐름 예 (물체 3개, T8 옵션을 켠 경우):

| 시각(초) | 레이더 | 팔 |
|---|---|---|
| 0~1.4 | 한 방향 회전, 후보 발견 | 대기 |
| 1.4~ | 돌아오는 회전 계속(팔 자리는 지움) | 후보로 출발, 가는 길이 첫 확인선 |
| ~7 | 멈춤(팔 센서 우선) | 확인 끝 → 집기 → 놓기 |
| 놓는 동안 | 4바퀴 돌려 합침 | 배출 구역 |
| 다음 | 결과 준비됨 | 다음 후보로 바로 출발 |

### 3.4 ESP32 배선과 전원
팔 쪽(PC ─USB─ Seeed 모터 보드 ─ 팔 서보 6개, 12V 5A 어댑터)은 그대로 둔다. ESP32를 PC에 USB로 하나 더 꽂는다. PC에서는 COM 포트가 두 개가 된다.

```
PC ─USB(데이터)─ ESP32 ─┬─ 레이더 HC-SR04  TRIG 25, ECHO 26 (분압)
  (팔 받침 옆에 고정)    ├─ 팔 HC-SR04     TRIG 32, ECHO 33 (분압) ─ 1.5m 케이블로 손목까지
                         └─ 레이더 서보 (driver에 따라)
                              pwm: MG90S 신호 GPIO 13 ─ 60cm 연장선
                              dxl: UART2 GPIO 17(TX)→OpenRB Serial2 RX, GPIO 16(RX)←OpenRB Serial2 TX, GND 공통 ─ OpenRB-150 ─ XL330
HC-SR04 2개 전원: ESP32 5V(VIN) 핀 (개당 약 15mA)
서보 전원: 아래 A 또는 B. 모든 GND는 하나로 묶음
```

| 연결 | ESP32 핀 | 비고 |
|---|---|---|
| 레이더 TRIG | GPIO 25 | |
| 레이더 ECHO | GPIO 26 | 분압 1kΩ/2kΩ로 5V → 3.3V |
| 팔 센서 TRIG | GPIO 32 | |
| 팔 센서 ECHO | GPIO 33 | 분압 1kΩ/2kΩ |
| 서보 신호 (pwm) | GPIO 13 | LEDC PWM 50Hz |
| OpenRB 연결 (dxl) | GPIO 17 = UART2 TX, GPIO 16 = UART2 RX | 115200bps, 3.3V ↔ 3.3V(분압 필요 없음), TX/RX 교차, GND 공통. OpenRB 쪽은 Serial2 단자(2mm 1x4 핀 헤더 소켓 납땜 필요, 사용자 보고) |

**XL330 전원은 5V다(결정 0043).** 입력 범위가 3.7~6.0V라 **12V를 OpenRB VIN에 넣으면 XL330이 망가진다.** 배선 전에 OpenRB VIN 단자 전압을 멀티미터로 확인한다(사용자 결정 대기 U4, `work-queue.md`). OpenRB의 DXL 포트 전원은 VIN(전원 점퍼를 VIN(DXL) 쪽)에서 오고 FET가 꺼진 채 켜지므로 펌웨어가 핀 31을 켠다. USB-C만으로는 500mA 퓨즈라 정지 토크 1.47A를 못 받는다. 전류는 움직이기 시작할 때 최대 약 1.5A라 5V 2A 이상을 쓴다(MG90S는 0.5~0.8A였다). ESP32의 5V 핀에서 쓰지 않는다(리셋되면 센서 통신이 끊겨 작업이 멈춘다).

| 방법 | 구성 | 판단 |
|---|---|---|
| A. USB 5V 충전기 | 5V 3A 충전기 → USB-A 단자 보드 → OpenRB VIN 단자(점퍼 VIN(DXL)). 충전기 GND와 ESP32 GND 연결. 단자에 470µF. (pwm이면 서보 빨강·갈색에 직접, 신호는 GPIO 13) | 팔 전원과 완전히 분리. 팔 전원 사건(서보 6개 동시 토크 꺼짐 3회) 원인을 찾기 전에는 진단이 섞이지 않는다 |
| **B. 기존 12V 5A 어댑터 공유 (강압 모듈 방식은 0035에서 왔고, 지금 근거는 결정 0043-2)** | 어댑터 출력을 DC Y 분배 케이블로 나눠 한쪽은 모터 보드, 한쪽은 12V→5V 강압 모듈(3A급, 출력 5.0V로 맞춤, **멀티미터로 5.0V 확인한 뒤** 연결) → OpenRB VIN 단자. GND 공통, 470µF | 전기적으로 충분하다. 팔 최대 1.7A(powertest) + 서보 최대 약 1.5A×5V/12V ≈ 0.6A(12V 기준) = 약 2.3A로 5A의 약 46%. 다만 팔의 과전류 감시(4A)는 팔 서보 전류만 재므로 이 부하를 모르고, 어댑터 보호가 걸리면 레이더도 같이 꺼진다. 모터 보드의 남는 서보 포트에서 12V를 따지 않는다 |

## 5. 레이더 처리 (`radar.py`)
1. **기준값(C1)**: 빈 작업대에서 3바퀴(정방향·역방향·정방향)를 돌려 각도별 중앙값을 저장한다. 바퀴 사이 차이가 20mm를 넘는 각도는 "불안정"으로 표시하고 후보에서 뺀다. 저장: `runs/<시각>/scans/baseline.json`, 최근 값은 `config/ultrasonic_baseline.json`(git 제외).
2. **바퀴 합치기**: 각도별로 그 판단에 쓸 바퀴 값(처음엔 1~2바퀴, 놓는 동안엔 4바퀴)의 중앙값. 응답 없음은 빼고 센다. 처음 1~2바퀴로 후보가 없으면 바로 끝내지 않고 `radar.empty_extra_sweeps`(기본 3)바퀴를 더 돌려 합친 값으로 다시 판단한다. 근거: 8.5절 벤치마크 비관 `single` 51→74%(커밋 fa7c409).
3. **후보**: 기준값보다 30mm(`dip_mm`) 이상 가까운 각도가 2개 이상 이어지면 호 하나. 거리가 25mm 넘게 바뀌면 다른 호로 자른다. 붙어 있는 호(각도 이웃, 대표점 사이 110mm 이하)는 한 물체로 합친다. 대표점은 호들의 (각도 중앙, 거리 중앙값) 평균이고, 후보 위치 = 대표점 + 센서 방향으로 15mm.
4. **팔 지우기**: 그 측정 시각의 팔 관절값으로 링크 점(어깨, 팔꿈치, 손목, 손끝)의 작업대 xy를 구한다. 그 점의 방위 ±(빔 반각 + 5°) 안이면서 거리 차가 60mm 안인 측정은 버린다.
5. **도달 범위**: 후보가 `workspace.yaml`의 `reach_mm` 밖이면 표시만 하고 고르지 않는다. 단, **확인 전 레이더 후보는 집는 범위(`pick_reach_mm`)보다 바깥으로 60mm 여유를 두고 거른다**(2026-11-15, REQ-065). 레이더 후보는 물체의 레이더 쪽 면(팔에서 먼 쪽)으로 치우쳐 반경이 크게 나온다(참값 222mm → 후보 260mm 사례, 후보 오차 90%가 56~63mm). 여유 없이 거르면 집을 수 있는 물체가 CHECK 전에 빠져 `no_objects`로 끝난다. 여유는 설정 키로 두고(이름은 코드가 기준), 확인 뒤 확정된 물체와 수동 입력 물체는 지금처럼 `pick_reach_mm` 그대로 거른다(집는 범위는 넓히지 않는다). 확정 위치가 집는 범위 밖이면 집지 않고 그 후보를 건너뛴다. 여유는 `config/workspace.yaml`의 `candidate_reach_margin_mm`(60)이고 최대 반경에만 더한다(최소는 그대로). 벤치마크(8.5절)도 같은 정책 함수(`policy.choose(unconfirmed=True)`)로 후보를 거른다(#391).
6. **출력**: `ScanResult.objects`에 후보(`angle_deg=None`, 폭·길이 0, `confidence` 0.1~0.3), `raw`에 각도별 바퀴 값·기준값·호·지운 각도.

## 6. 팔 확인 처리 (`check.py`)
손끝 높이는 3.3절 확인 높이로 고정, 손끝은 수직 아래다. **손목 yaw는 후보마다 한 값으로 정한다(결정 0065)**: 후보의 반경 r(팔 원점 기준)에서 센서가 손끝보다 바깥(반경 방향)으로 나가는 양이 c = clamp(r − `check.yaw_pivot_mm`(150), ±센서 옆 오프셋 66.5mm)이 되는 yaw다. 가까운 후보는 센서가 손끝 안쪽, 먼 후보는 바깥쪽에 와서 손끝 반경이 r − c(반경 100에서 150, 240에서 173.5)로 도달 범위 가운데에 머문다. 센서가 지나가는 선은 아래 표 그대로다. **도달 범위에 안 드는 선은 yaw를 나눠 간다(결정 0075-2)**: 후보 yaw로 도달 범위(`check.tool_reach_mm`)에 다 들지 않는 선은 후보 yaw에 `check.line_yaw_alt_deg`([−90, −45, 45, 90])를 더한 yaw 가운데 둘까지 골라 조각으로 나눠 간다. `ik_fail`이면 첫 점을 당기기 전에 그 조각이 도달 범위에 드는 다른 yaw로 먼저 다시 낸다. 그래서 손목은 확인 중 단계와 조각 사이에 돈다(후보 yaw에서 최대 ±90°). 다 드는 선은 후보 yaw 하나로 간다(0065 그대로). 조건을 만족하는 yaw 해는 둘이고 `check.yaw_deg`(90)에 가까운 쪽을 쓴다(손목이 덜 돈다). 옵션을 끄면(`yaw_pivot_mm`이 0이거나 없음) 전처럼 `yaw_deg` 고정이다. 센서 값 `h = 센서 높이 − 거리`가 15mm 넘으면 "물체 위"다. 측정은 30Hz, 팔 100mm/s에서 약 3.3mm마다 한 번.

| 단계 | 경로 | 얻는 것 |
|---|---|---|
| L1 | 후보를 지나는 길이 180mm 직선. 작업대 x축 방향. 옵션 `check.approach_line`을 켜면 팔 원점에서 후보로 가는 방향(접근 경로 겸용, T8) | 그 방향 중심 |
| L2 | L1 중심을 지나는 수직 직선 180mm | 다른 방향 중심 → 1차 중심 |
| R | 1차 중심 둘레 원, 36점. 반지름은 (L1 구간 길이 + L2 구간 길이)/4를 35~75mm로 자른 값(`check.ring_auto_mm`, 결정 0075-1). 원이 짧은 축 끝과 긴 축 끝 사이를 지난다. 끄면 `check.ring_r_mm`(60) 고정(2026-11-14 #359에서 45 → 60). 60 고정은 40×80 물체의 빔 넓힌 긴 축 반길이(약 55mm)보다 커서 모서리만 스쳐 φ가 대각선 쪽으로 쏠렸다 | 물체가 걸리는 방향들 → 긴 축 각도 φ(두 배 각도 평균), 강도 R |
| L3 | 중심을 지나는 φ 방향 직선 180mm | 긴 축 방향 중심과 길이 |
| L4 | 같은 중심을 지나는 φ+90° 직선 180mm. L3와 한 번의 `follow_path`로 이어서 간다 | 짧은 축 중심과 폭 → 최종 중심(L3·L4의 치우침을 함께 더함) |

- 각 직선은 후보 중심(0)을 품거나 가장 가까운 메아리 구간을 고른다. 중간의 응답 없음 1칸은 이어 본다. T9(중심을 지난 구간이 끝나고 3칸 비면 멈춤)는 지금 끈다(4절).
- **방향**: R > 0.3이면 `angle_deg = φ`(0~180, 연속값). 비교 실험에서는 가까운 0/45/90/135°로 묶는다. R ≤ 0.3이면 정사각형·원형으로 보고 `angle_deg=None`, 집기는 기본 각도로 한다.
- **크기**: L3·L4 구간 길이 − 2 × 빔 반경. 빔 반경 = (센서 높이 − 물체 높이) × tan(빔 반각), 빔 반각은 B1 실측값(그 전에는 7.5°).
- **물체 높이**: 구간 안 `h`의 중앙값. `raw`에 남긴다(집는 높이 참고용).
- **신뢰도**: 0.5 + 0.5 × min(R, 1), 구간이 끊겼거나 L3·L4 중심 차이가 10mm를 넘으면 0.2를 뺀다.
- **도달 범위로 자르기**: 확인 경로(L1~L4, 원, 실패용 격자)의 점 가운데 손끝이 도달 범위 밖인 점은 건너뛴다. 범위는 `check.tool_reach_mm`(팔 원점 기준, 그리퍼별 `check.tool_reach_by_gripper`: 병렬 95~230mm, 단동식 100~255mm, 1절)이다. H-2 뒤 도달 계산(손끝 수직 아래, 접근 높이 60mm, REQ-090)의 값이다. 판단은 센서 점을 손끝 점으로 바꾼 뒤 `check.py`가 한다(8.2절, 팔 모듈 import 없음). 메아리 구간이 잘린 끝에 닿으면 그 직선은 중심이 치우칠 수 있어 신뢰도를 0.2 낮춘다. 그래도 `follow_path`가 경로 중간에서 멈추면(IK 실패) 그때까지의 샘플만 쓴다.
  - 근거(기획 초기 계산, 물체 1개, 레이더 오차 σ 25mm. 초음파 세션 계산으로도 물체 1개에서 구간째 건너뜀 57% → 점만 건너뜀 96%로 같은 방향): 직선 ±90mm에 자르기를 쓰면 반경 100~200mm에서 83~93%, 200~240mm에서 77~89%다. 직선을 ±60mm로 줄이면 62~93%로 더 나빴다. 100mm 막대는 빔 번짐까지 ±70mm가 필요해 양 끝을 못 보기 때문이다.
  - **시연 배치 규칙**(A1·I1·시연이 모두 이 하나를 쓴다, 2026-11-20 drift-report로 하나로 정함): **반경 150~220mm**(2026-11-20 사용자 승인으로 120 → 150. MuJoCo 집기 시험장 M5에서 병렬 손이 반경 120·방위 ±40°에서 `blocked` 24건, `project-status.md` 8절 1), **방위 45~135°**(정면 ±45°, 결정 0067: 판 425×375에서 반경 220의 양 옆이 판 밖이다), 물체 몸체가 판 안, **물체 중심이 통 무시 원(반 대각선 + 벽 + `safety_margin_mm` = 112.8mm) 밖**, 물체 몸체가 통 벽(벽 두께 포함)과 안 겹침(반경 210·방위 −40°의 100×30 막대는 중심이 무시 원 밖인데 몸체가 벽에 걸린다). 벤치마크 `on_plate`·`_hits_zone`(`demo`·`demo80`·`spread*`)과 같다. 반경만 다르다: 고정 시나리오 `demo`·`demo80`·`spread*`는 1절 표·비교 실험(결정 0074)과 견주려고 120~220을 그대로 두고, 시연 규칙 그대로 뽑는 시나리오는 `show80`(반경 150~220, 나머지는 `demo80`과 같음, 8.5)이다. 무시 원 둘레에 50mm를 더 두는 것은 `pair_layout`만의 조건이라 쓰지 않는다. 그리고 물체 중심 사이 120mm 이상, **물체 모서리(가장 가까운 두 변) 사이 80mm 이상**을 권장한다(2026-11-15). 중심 간격만으로는 길이 100mm 물체가 긴 축을 마주 보면 모서리 간격이 20mm까지 내려가고, 센서 높이 154.5mm에서는 빔이 이웃을 합쳐 본다. 근거(옛 작업대 값): 벤치마크 `--scenario pair --pair-gap N`(씨앗 40, #379, 초음파 세션 값) 모서리 간격 10/20/30/40/50/60/80mm에서 성공 낙관 40/51/55/65/88/89/96%, 비관 46/48/52/56/51/49/86%. 낙관은 50mm, 비관은 80mm부터 따로 보인다. B1(빔 반경) 실측 뒤 다시 정하고, I1과 시연 배치는 이 조건으로 놓는다. 고정 시나리오 `demo`·`spread*`는 중심 간격만 보고, 모서리 간격 조건을 더한 것이 `demo80`이다(#384). 네 시나리오 모두 반경(120~220)만 빼고 위 배치 규칙으로 뽑는다(H-4, 1절 표).
  - 그 밖도 집기는 하지만 확인 성공률이 낮다(8.5절 벤치마크 `single` 반경 220mm 이상, `spread90` 비관에서 약함).
- **첫 점 당기기**(U16 안 A, 2026-11-15 사용자 승인. CHECK에만 쓴다): `tool_reach_mm`으로 자른 뒤에도 경계 근처 점은 IK가 안 풀릴 수 있다. `follow_path`는 한 점이라도 안 풀리면 움직이지 않고 `ik_fail`로 끝나므로, 그 단계 전체를 잃는다(U16 전 병렬 `demo` 비관 50%, 당기기 85mm 뒤 63%, 1절).
  - 작업 실행이 `follow_path` 결과의 상태를 `probe.feed(poses, status)`로 넘긴다(8.2절). 상태가 `ik_fail`이고 샘플이 비었으면 `Probe`는 그 단계를 버리지 않고, **그 단계 경로의 첫 점을 첫 구간을 따라 둘째 점 쪽으로 `check.retry_pull_mm`(2mm)씩 당긴 경로**를 다음 `next_segment()`로 다시 낸다.
  - 당기는 거리의 합은 `check.retry_pull_max_mm`(**85mm**, 2026-11-17 확정)까지다(단계마다 최대 42번). 첫 구간의 남은 길이가 5mm 아래로 내려가면 그만둔다(너무 짧은 첫 구간을 만들지 않는다). 그래도 `ik_fail`이면 지금처럼 그 단계를 unreachable로 건너뛰고 신뢰도를 0.2 낮춘다. 끝 점은 당기지 않는다(끝 점 때문에 남는 `ik_fail`이 벤치마크에서 보이면 U9에서 따로 본다).
  - 다시 부르는 것은 `ik_fail`뿐이다. `out_of_bounds`(안전 검사)·`plan_too_slow`·`stopped`·fault는 다시 부르지 않는다.
  - 실패한 호출은 팔이 움직이기 전에 끝나므로 팔 동작 시간은 늘지 않는다. 늘어나는 것은 계획 계산 시간(단계마다 최대 42번, 벤치마크 평균 4번 안팎)이고, 구현 PR에서 한 번의 실패 호출이 걸리는 시간을 재서 적는다. 당긴 만큼 그 직선의 시작이 짧아지므로 메아리 구간이 잘린 끝에 닿으면 기존 규칙대로 신뢰도를 0.2 낮춘다.
  - 기록: 당긴 단계 이름과 거리(mm)를 `checks/NNN.json`의 `info`에 남기고, `US-CHECK` 이벤트에 당긴 횟수를 넣는다.
  - `retry_pull_max_mm: 0`이면 끈다(U16 전 동작).
  - **상한 측정 계획**(2026-11-16 밤, 사용자가 기획에 맡김): 초음파 세션이 병렬 실제 기구학(`--reach kin --gripper parallel`, 75~250), 씨앗 20으로 `single`·`demo`·`demo80`을 아래 네 설정에서 잰다. (가) `retry_pull_max_mm=40` (나) `=60` (다) `=85`(직선 반 길이 90mm에서 남길 5mm를 뺀 값 = 사실상 끝까지) (라) `=40`에 `retry_pull_mm=1`. 설정마다 성공률(낙관·비관), 인식 평균·90%·최대, **단계당 다시 부른 횟수의 평균·최대**를 낸다. 고르는 규칙: 세 시나리오의 비관 성공률 평균이 가장 높은 설정에서 2%p 안에 드는 것 가운데 상한이 가장 작은 것. (라)가 (가)보다 2%p 넘게 좋을 때만 간격을 1mm로 바꾼다. 고른 설정은 총괄이 다시 돌려 확인하고, 그 값으로 8.3의 숫자와 1절 표를 바꾼다. 다시 부르는 횟수가 단계당 평균 10번을 넘으면 실패 호출 1회의 계획 시간(`--sim`으로 잰 값)과 함께 보고한다(시간이 문제면 간격을 넓힌다).
  - **측정 결과(2026-11-17)**: 비관 평균이 가장 높은 (다) 85(71.7%)에서 2%p 안은 (다)와 (라)(70.0%)다. (라)는 간격 1mm 조건((가)보다 2%p 넘게 좋음)을 못 채워((가)보다 +0.7%p) 2mm 간격의 (다)가 남는다. 그래서 `retry_pull_mm` 2, `retry_pull_max_mm` 85로 정했다. (나)와 (다)의 차이는 씨앗 잡음(±5%p) 안일 수 있으나 규칙대로 고른다. 다시 부른 횟수는 단계당 평균 3.7~12.2((라)가 가장 많음), (다)는 4번 안팎이라 계획 시간 보고는 필요 없다. 값과 표는 1절.
  - **벤치마크**: `--trim-start`(가상 팔 쪽에서 1mm씩 당기던 것)는 없앴다(REQ-067). 실제 기구학 모드(`--reach kin`)의 가상 팔이 실제 팔처럼 `ik_fail`을 돌려주고, 당기기는 위의 실제 `Probe` 코드가 한다(결정 0037: 같은 코드). 반경 도달 모델에서는 `ik_fail`이 없어 해당 없다. 구현 뒤 병렬 `single`·`demo`·`demo80`을 75~250으로 다시 재서 1절 병렬 표를 한 열로 바꿨다(2026-11-17).
- **실패**: L1·L2 모두 메아리가 없으면 후보 둘레 100×100mm를 20mm 격자로 한 번 훑는다. 그래도 없으면 후보를 지우고 `DECIDE`로 돌아간다(레이더 오검출). 같은 자리가 두 번 실패하면 그 사이클에서 다시 고르지 않는다.
- **안전**: 모든 이동은 기존 안전 검사(관절 한계, 작업 영역, 바닥, 결정 0015·0031)를 거친다. 확인 높이가 물체 높이 + 15mm보다 낮아지는 설정은 거부한다. E-STOP·정지는 그대로 동작하고, 확인 중 정지면 ESP32에 `stop`을 보낸다.

## 7. ESP32 ↔ PC 통신 규약 (`system-architecture.md` 6절 대체)
- USB 시리얼 921600bps(보드가 안 되면 115200), 한 줄에 JSON 하나. 측정 줄은 짧은 키로 40바이트 안팎.
- ESP32는 측정마다 자기 시계(µs)를 붙인다. PC는 연결할 때와 10초마다 `sync`로 시계 차이를 구해 PC 단조 시계로 바꾼다(왕복 시간의 절반을 빼는 방식). 목표 오차 2ms 이하(팔 100mm/s에서 0.2mm).
- 측정 간격: 어느 센서든 앞 측정과 33ms(`ping_gap_ms`) 이상 띄운다. 두 센서가 다 켜져 있으면 팔 센서가 우선이고, 팔 센서가 측정하는 동안 레이더는 멈춘다.

| 방향 | 메시지 | 뜻 |
|---|---|---|
| PC → | `{"cmd":"hello"}` | 펌웨어 버전, 센서·서보 종류 묻기 |
| PC → | `{"cmd":"sync","pc":<ns>}` | 시계 맞추기 |
| PC → | `{"cmd":"sweep","from":10,"to":170,"step":4,"bounce":true,"sweeps":N,"max_mm":600}` | 레이더 회전. N=0이면 `stop`까지 계속 |
| PC → | `{"cmd":"stream","hz":30,"max_mm":300}` | 팔 센서 연속 측정 시작 |
| PC → | `{"cmd":"stop"}` | 회전·연속 측정 멈춤. 서보는 그 각도 유지 |
| PC → | `{"cmd":"servo","deg":90}` | 서보 각도(대기 자세) |
| PC → | `{"cmd":"driver","name":"pwm"\|"dxl"}` | 서보 구동 고르기(`servo.driver`, 연결할 때 PC가 보냄). 응답은 `hello`(servo가 바뀐 값). 펌웨어는 켤 때 항상 pwm이다 |
| PC → | `{"cmd":"once","k":"r"\|"a"\|"ra","n":5,"max_mm":600}` | 한 자리에서 n회(실측용). "ra"는 레이더·팔 센서를 번갈아. 끝나면 `done` |
| PC → | `{"cmd":"gap","ms":33}` | 측정 간격(`ping_gap_ms`) 바꾸기(실측 B3용). 응답 `gap` |
| ← ESP32 | `{"t":"hello","fw":"0.3","servo":"pwm"\|"dxl","k":["r","a"]}` | |
| ← ESP32 | `{"t":"sync","pc":<ns>,"us":<µs>}` | |
| ← ESP32 | `{"t":"r","a":86,"d":312,"us":<µs>}` | 레이더 측정. a = 명령 각도(°), d = mm, 응답 없음은 `null`. dxl이면 선택 필드 `"ang":85.7`(측정 직전에 OpenRB가 알려 준 실제 각도, 0.5초 안에 못 받으면 생략). 하위 호환: `ang`가 없으면 `a`를 그대로 쓴다 |
| ← ESP32 | `{"t":"a","d":104,"us":<µs>}` | 팔 센서 측정 |
| ← ESP32 | `{"t":"end","dir":1,"us":<µs>}` | 한 방향 회전 끝 (dir 1 = 증가, −1 = 감소) |
| ← ESP32 | `{"t":"done"}` | `once` 끝 |
| ← ESP32 | `{"t":"gap","ms":33}` | 바뀐 측정 간격 |
| ← ESP32 | `{"t":"err","msg":"..."}` | 오류 |

- **ESP32 ↔ OpenRB 줄 규약** (UART2 115200, ASCII 한 줄): ESP32 → OpenRB `g <deg×10>`(목표 각도, 0~1800 = 0.0~180.0°, 90° = 정면), OpenRB → ESP32 `p <deg×10>`(읽은 실제 각도, 약 5ms마다), 오류 `e 1`(XL330 ping 실패)·`e 2`(읽기 응답 없음). ESP32는 `e` 줄을 PC에 `err`로 올린다. 영점 눈금(서보 90° = 2048)과 방향은 OpenRB 펌웨어 상수(`ZERO_TICKS`, `DIR`)이며 조립 뒤 B4에서 맞춘다.
- 연결이 1초 넘게 끊기면 `UltrasonicSource`는 오류를 내고 작업 실행은 `FAULT`로 간다(팔 통신 끊김과 같은 처리, 결정 0031). 센서 응답 없음(`null`)은 오류가 아니다.

### 8.2 인터페이스 (`system-architecture.md` 4·5절에 추가)
```python
@dataclass
class PathSegment:                 # 작업대 좌표, 손끝(TCP)은 수직 아래
    points_mm: list[tuple[float, float]]   # 손끝 xy (센서 xy 아님)
    tool_z_mm: float
    speed_mm_s: float                       # 실제 속도 = min(이 값, tool_v_max_mm_s × 속도%)
    yaw_deg: float | None = None            # 경로 동안 고정할 손목 각도. None = 지금 값 유지

@dataclass
class PoseSample:                  # 팔 50Hz 루프의 실제 관절값으로 계산
    t_ns: int                      # PC 단조 시계
    tool_mm: tuple[float, float, float]     # 손끝 위치 (작업대 좌표)
    sensor_mm: tuple[float, float, float]   # 팔 센서 위치 = 손끝 + 도구 축으로 옮긴 arm_sensor_offset_mm = 손끝 + R(yaw)·(−off.x, off.y), z는 + off.z

class CheckProbe(Protocol):
    def next_segment(self) -> PathSegment | None: ...
    def feed(self, poses: list[PoseSample], status: str = "ok") -> None: ...   # status = follow_path 결과 상태(MotionResult.status). "ik_fail"이고 poses가 비면 첫 점을 당겨 다시 낸다(6절 첫 점 당기기, U16)
    def result(self) -> DetectedObject | None: ...   # None = 물체 없음. height_mm = 확인한 실측 높이(결정 0042, 0 = 모름)

class CheckableSource(PerceptionSource, Protocol):
    def start_check(self, candidate: DetectedObject) -> CheckProbe: ...
    def prefetch(self, arm_links_fn) -> None: ...    # 놓는 동안 레이더 미리 돌리기 (T5)
    def rescan(self) -> ScanResult: ...              # RESCAN (2절): 팔이 대기 자세일 때 4바퀴
    def begin_cycle(self) -> None: ...               # 작업 실행 시작 때 한 번: 지운 자리·실패 수를 비움
    def note_failure(self, x_mm: float, y_mm: float) -> None: ...   # 집기 실패·못 가서 못 잰 자리를 알림
    @property
    def give_up(self) -> bool: ...                   # 실패 수가 check.max_fail_per_run에 닿으면 True
```
작업 실행의 `CHECK`:
```python
probe = source.start_check(cand)
while (seg := probe.next_segment()) is not None:
    poses = arm.follow_path(seg.points_mm, seg.tool_z_mm, seg.speed_mm_s, seg.yaw_deg)   # REQ-023
    probe.feed(poses, arm.last_path.status)   # U16: 상태를 같이 넘긴다
obj = probe.result()
```
- `follow_path` 한 번의 호출은 멈추지 않고 이어서 간다. 꺾이는 점에서 서지 않고(`move_p`처럼 블렌딩), 완전히 서는 것은 처음과 끝에만 한다. 한도는 기존 `tool_v_max_mm_s`·`tool_a_max` 그대로이고 **한도가 우선한다**. 꺾이는 점(L3 끝 → L4 시작 등)과 원에서는 가속 한도를 넘지 않을 만큼 속도를 줄여 지나간다(원은 v²/반지름 ≤ `tool_a_max`). 줄인 속도는 `PoseSample` 시각에 그대로 남으므로 `check.py`는 따로 보정하지 않는다. 8.5절 벤치마크의 가상 팔도 같은 규칙으로 속도를 줄인다. 지금 손끝 위치에서 첫 점까지 옮겨 가는 것도 같은 호출에 넣는다. `check.py`는 다음 선의 시작점을 지금 위치에서 가까운 끝으로 고른다.
- **실패 알림**: 작업 실행은 `PICK`이 실패하면 `source.note_failure(x, y)`를 부른다. 확인에서 물체가 없거나 못 간 경우는 인식 모듈이 스스로 센다. 같은 자리(`merge_mm`/2 안)가 두 번째 실패면 그 작업 실행에서 다시 고르지 않는다. 작업 실행은 `DECIDE` 전에 `source.give_up`이 True면 `DONE`으로 간다. 근거: 8.5절 벤치마크(커밋 c3b47d8)에서 알림을 넣으면 성공은 그대로이고 최대 인식 시간이 217→120초로 줄었다. 상한 3은 성공 -1%p 안에서 비관 꼬리를 더 줄였다(`demo` 비관 90% 85→67초).
- **높이 다시 재기**(결정 0052): 후보의 높이를 모르고 수직으로만 집을 수 있으면(`tilt_ok=False`), 작업 실행이 그 후보를 한 번 더 `CHECK`해 높이를 얻는다. 수직 집기가 `no_object`여도 한 번 더 `CHECK`하고 한 번만 다시 집는다. 두 번째 실패는 위의 `note_failure`로 센다.
- 경로는 손끝 기준이다(2026-11-05 사용자 승인). `check.py`는 센서가 지나갈 선(6절)을 정한 뒤, 그 구간의 yaw로 옮긴 센서 오프셋 R(yaw)·(−off.x, off.y)(`check.sensor_offset_xy`, 결정 0075-3)를 빼서 손끝 점으로 바꿔 `PathSegment`에 넣는다. 이 식은 팔 `ArmService.sensor_position`(`tool_axes(q) @ off`, 손이 아래를 보아 거울이다)과 같고, `sensor_to_tip`·`pick_yaw`·벤치마크 가상 팔이 같이 쓴다. 이 변환은 `check.py` 한 곳에서만 한다.
- `probe.feed`는 그 구간 시각 범위의 ESP32 팔 센서 측정을 `PoseSample`과 시각으로 맞춰(선형 보간) 점(x, y, h)으로 바꾼다.
- 인식 모듈은 팔 모듈을 import하지 않는다. 팔 링크 위치는 작업 실행이 `arm_links_fn`으로 넘긴다(의존 방향 `system-architecture.md` 2절 유지). 예외는 검증 도구인 `benchmark.py`(8.5절)뿐이다: 가상 팔이 실제 궤적과 같도록 `arm/trajectory.py`를 읽는다. `radar.py`·`check.py`·`source.py`는 팔을 import하지 않는다.
- 이벤트(`Studio.bus`): `us.sweep`(각도별 값), `us.candidates`, `us.check_path`(구간과 점), `us.check_result`. GUI는 이것으로 그린다(REQ-024).

### 8.5 성능 벤치마크 (결정 0037)
초음파 성능 숫자는 이 벤치마크로만 낸다. 초음파 세션이 만들고 관리한다. 실행은 `python -m so101_studio.perception.ultrasonic.benchmark [--scenario 이름] [--seeds N]`이고, 레이더·확인 코드는 실제 `radar.py`·`check.py`를 그대로 돌린다. 결과는 표로 내고, 커밋과 시나리오 이름을 함께 남긴다(`runs/bench/`). 새 아이디어(확인선 길이, 모드, 속도 등)는 이 벤치마크의 옵션으로 붙인다.

### 8.4 기록
- `runs/<시각>/scans/NNN.json`: 레이더 바퀴별 원자료, 기준값, 호, 후보, 지운 각도.

- **정답 쌍**(결정 0072, 2026-11-19 · 2026-11-20 REQ-096 #497 구현에 맞춤): R1·A1·I1 실측에서는 사람이 놓은 물체의 정답(자리 표시 x, y, 각도, 크기, 높이)을 남긴다. 정답 쌍 실행은 `runs/ultrasonic-truth/<시각>-<시험>/`에 `truth.json`·`scans/`·`checks/`를 함께 둔다(실행 폴더 정리 대상 밖, REQ-094). 실측 목록은 `runs/ultrasonic-truth/index.jsonl`(`run`, `test`, `commit`, `objects`, `placements`, `sim`)에 한 줄씩 더한다. 형식은 `perception/ultrasonic/truth.py` 머리말이다. R1은 `radar_check r1`이 남긴다. A1·I1은 8.6 초안의 명령(`checktest a1`, `run --source ultrasonic --truth-layout K`)으로 남길 계획이다. 12/4 뒤 "스캔 → 위치·크기" 지도학습 추정기(2차)의 학습 데이터다.

### 8.6 팔 확인 실측 도구 `checktest a1`과 I1 정답 기록 (초안, 2026-11-20. 구현 전 점검(결정 0048 Stage 9)의 꼭 고칠 것 8건을 같은 날 반영했다. 총괄이 합친 뒤 팔 REQ의 근거로 쓴다)
10절 A1(팔 확인 단독)과 I1(통합)을 돌리고 정답 쌍(8.4)을 남기는 도구다. R1은 `radar_check r1`(#497)이 이미 한다. A1은 정답 가까운 후보에서의 **확인 정확도만** 잰다. 오프셋 0~30mm는 실제 레이더 후보 오차(H-4 뒤 중앙 25~40mm, 90mm 안 100%)보다 쉽다.

**어디서 도나**
- A1은 팔을 움직이므로 `ArmService`를 거치는 팔 쪽 CLI 명령 `so101 checktest a1`이다. `radar_check`는 인식 모듈 안이라 팔을 import하지 못하고(8.2 의존 방향), `run --source ultrasonic`은 레이더·집기·놓기까지 돌므로 CHECK만 보는 A1과 맞지 않는다.
- I1은 레이더부터 집기·놓기까지 전부이므로 `run --source ultrasonic`에 정답 옵션 `--truth-layout K`만 단다.
- **A1은 레이더 쪽을 쓰지 않는다**(`scan`·`prefetch`를 부르지 않는다). 그래서 레이더 조립과 B2·B4·R1 없이 할 수 있다. 필요한 것은 손목 센서(브래킷 장착)·ESP32·팔(로보나인)과 A0이다. B1이 없으면 크기 추정은 가정 빔 반각(7.5°)으로 한다. 서보 쪽 보드(OpenRB·XL330)가 없거나 덜 꽂혔으면 `config/ultrasonic.local.yaml`의 `servo.driver`를 `pwm`으로 둔다(`dxl`인데 OpenRB가 오류 줄을 보내면 소스가 예외를 낸다). 레이더가 늦으면 A0·A1을 먼저 한다.

**명령**(CLI는 전역 옵션 + 위치 인자 `values`인 평평한 argparse다. `a1`은 `values[0]`이고 아래 옵션은 모두 전역 옵션이다)
```
so101.cmd --speed 30 checktest a1 --us-port COMx [--obj 40x80x40] [--offset 30] [--seed 0] [--reps 1] [--note 메모]
so101.cmd --sim checktest a1                       # 가상 ESP32·가상 팔, 사람 입력 없음(물체를 정답 자리에 놓는다)
so101.cmd --speed 30 run --source ultrasonic --us-port COMx --truth-layout 3 [--note 메모]   # I1 배치 3번(1~10)
so101.cmd --sim run --source ultrasonic --truth-layout 3                                    # 같은 배치를 가상 ESP32에
```
- `--obj 폭x길이x높이`(mm), `--offset` 후보를 정답에서 떨어뜨리는 최대 거리(mm), `--seed` 후보 씨앗, `--reps N` 12회 묶음을 N번(정답 쌍을 늘릴 때만), `--note` `truth.json` 메모.

**A1 자리와 순서**(한 묶음 12회 = 3자리 × 4방향, 1절 A1 기준과 같은 수)
| 자리 | 작업대 좌표(mm) | 팔 원점 기준 반경·방위 | 통 무시 원 가운데 (355, 80)까지 |
|---|---|---|---|
| S1 | (189, 169) | 150mm · 100° | 188mm |
| S2 | (125, 177) | 180mm · 120° | 250mm |
| S3 | (270, 224) | 210mm · 75° | 167mm |
- 팔 원점은 `workspace.yaml`의 `robot_base_in_table` (215.2, 21.4)이다. 세 자리는 6절 시연 배치 규칙(반경 150~220, 방위 45~135°, 중심이 통 무시 원 112.8mm 밖, 몸체가 판 안이고 통 벽과 안 겹침)을 지키고, 가까움·가운데·멂과 방위 75·100·120°로 정면 양쪽을 덮는다. 통 벽은 두께 포함 x 297~413·y 22~138이고, S3에 긴 축 135°로 놓아도 40×80 몸체가 닿지 않는다. 세 자리 모두 반경 150 이상이라 규칙을 150으로 올린 뒤에도 그대로다. 작업대 실측(H-6)으로 팔 원점이나 통 자리가 바뀌면 같은 규칙으로 다시 고른다.
- 방향은 긴 축 0·45·90·135°(작업대 x축 기준, 벤치마크 물체와 같음)다. 자리마다 네 방향을 차례로 해서 사람은 물체를 돌리기만 한다(n = 1~12: S1 0·45·90·135°, S2 …, S3 …).
- 시작 전 거부: `--obj` 높이가 `check.max_object_height_mm`(40)보다 크면 끝낸다(확인 높이가 고정이라 물체에 닿는다, 아래 안전).

**후보**(`a1_plan`이 시작 전에 모두 만든다)
- 후보 = 계획 자리(S1~S3) + 오프셋. 오프셋 방위는 0~360° 균등, 거리는 0~`--offset`(기본 30mm) 균등이고 `random.Random(f"a1-{seed}-{rep}-{n}")`로 고정한다(같은 씨앗이면 같은 후보).
- 후보는 레이더 후보와 같은 꼴이다: `DetectedObject(f"a1-{rep}-{n}", x, y, None, 0.0, 0.0, 0.3, "ultrasonic")`(`source.py`의 후보 만들기와 같음, 높이 0 = 모름).
- 사람이 실제로 놓은 값을 적으면 **정답만** 그 값으로 바꾸고 후보는 그대로다.

**한 회의 흐름**
1. 팔을 `poses.radar_clear`로 보낸다. 사람이 물체를 놓는 동안 팔이 비켜 있고, 작업 실행의 첫 `CHECK`와 같은 자세에서 출발한다. 결과가 `ok`가 아니면 그 회를 실패로 남기고 멈춘다(아래 판정).
2. 화면 두 줄: `n/12: S1 (189, 169)에 물체 중심, 긴 축 45°. 놓고 손을 뺀 뒤 Enter` / `(다르게 놓았으면 "x y 각도", q = 끝)`. `--sim`은 묻지 않고 `src.esp.boxes`를 정답 하나로 바꾼다(`radar_check._sim_source`와 같은 방식).
3. `before = len(src.saved)` → `runner.check_candidate(후보)` → `run.add([정답], src.saved[before:], rep)`(`radar_check.r1`과 같은 순서). 후보·결과·상태는 `checks/NNN.json`에 이미 들어간다(`candidate`, `result`, `status`). 확인마다 `end_check`가 한 번 쓰므로(`aborted` 포함) 회마다 `checks`는 정확히 1개, `scans`는 0개다.
4. 한 줄 출력: 상태, 위치 오차(mm, 결과와 정답 중심 사이), 방향 맞음, 확인 시간(`run_a1`이 `check_candidate` 앞뒤 시각으로 잰다).
- 정답: `truth.obj(x, y, 각도, 폭, 길이, 높이, id="P1")`. 폭 = 길이(정사각형)면 `angle_deg`는 `None`이고 그 회는 방향 판정을 빼고 위치만 본다(1절 "성공" 정의와 같음).
- `check_candidate`는 작업 실행의 `reachable(res, ws)` 거르기를 쓰지 않는다(A1은 집지 않고 확인 정확도만 잰다). 그래서 `checks/NNN.json`의 `status`와 A1의 상태가 같다.

**A1 판정**(`a1_summary`)
- 분모는 늘 12다(한 묶음). `ok`가 아닌 회(`empty`·`unreachable`·`aborted`, `radar_clear` 실패)는 위치 오차를 +∞로 두고 중앙값에 넣으며, 10mm 안 횟수와 방향 맞음 횟수에 넣지 않는다.
- 합격: 위치 오차 중앙값 5mm 이하, 10mm 안 11회 이상, 방향 맞음 10회 이상(벤치마크 `angle_ok`: 0~180° 주기로 22.5° 이하). `--obj`가 정사각형(폭 = 길이)이면 12회가 모두 정사각형이므로 방향 기준을 빼고 위치 두 기준만 본다.
- `aborted`(정지·고장·잠김)나 `radar_clear` 실패가 나오면 그 회를 실패로 남기고 **남은 회를 돌리지 않는다**(E-STOP 뒤 팔이 다시 움직이지 않게).
- `q`나 `aborted`로 12회 전에 끝나면 판정은 "미완료"이고 합격·불합격을 내지 않는다(남긴 회는 `truth.json`에 그대로 남는다).
- `--reps N`이면 묶음마다 12회로 따로 판정한다.
- 끝나면 판정, 기록 경로를 출력하고, `TruthRun.close()`가 `index.jsonl`에 한 줄을 남긴다.

**I1 정답 기록**(`--truth-layout K`)
- 배치: `i1_layout(k) -> list[Box]`는 `random_layout(random.Random(f"i1-{k}"), "show80")`의 물체 3개를 좌표 5mm·각도 5°로 반올림한 Box다(6절 시연 배치 규칙(반경 150~220)과 모서리 80mm 조건이 `on_plate`·`edge_gap`으로 들어 있다. 2026-11-20 반경 120 → 150으로 `demo80`에서 `show80`으로 바꿈). 반올림 뒤 `on_plate`·`edge_gap >= 80`을 다시 보고, 어기면 같은 rng로 다음 배치를 뽑는다(최대 20번, 결정적이라 K가 같으면 배치도 같다). 그래도 어기면 `RuntimeError`다. 반올림 뒤 다시 볼 때 반경 150 이상(팔 원점에서 물체 중심까지)도 본다(149.x가 반올림으로 생길 수 있다). `demo80` 때는 K = 1·2·6·8이 첫 배치에서 모서리 간격 77.4~79.8mm라 다음 배치를 썼다(REQ-097 #512). `random_layout`은 그때의 `workspace.yaml`을 읽으므로 작업대 설정이 바뀌면 배치 K도 바뀐다(`truth.json`에는 그때 값이 남는다).
- 정답: 물체 i(1~3)마다 `truth.obj(b.x, b.y, None if b.width == b.length else b.angle_deg % 180, b.width, b.length, b.height, id=f"P{i}")`.
- 실물: 배치를 화면에 보이고(물체별 크기·자리·각도) 사람이 놓은 뒤 Enter. `--sim`: `make_ultrasonic_source(..., boxes=i1_layout(k))`로 같은 반올림 값을 가상 ESP32에 놓는다(지금 `--sim`이 쓰는 기본 `demo` 배치 대신).
- 준비물: 크기(30×100·40×80·50×50, 높이 40)는 중복으로 뽑히므로 한 배치에 같은 크기가 3개까지 나올 수 있다. 크기마다 3개씩 준비한다.
- 배치 1~10 표(폭×길이×높이 mm, 중심은 작업대 좌표, 긴 축 각도, 50×50은 정답 각도 null)는 `show80`을 구현하는 PR이 지금 `workspace.yaml`로 다시 뽑아 이 자리에 넣는다. `demo80`(반경 120~220)으로 뽑은 #512 표는 반경 150 아래 물체가 있어 지웠다.
- 실행 하나가 정답 배치 하나다: `TruthRun("I1", src.cfg, sim=a.sim, note=f"log={svc.logger.dir} {a.note}")`를 열고 `src.record_dir = run.dir`, 작업 실행이 끝나면(성공·중단 모두 `try/finally`) `run.add(정답 3개, src.saved, 1)`와 `close()`. note의 `log=`가 그 실행의 `runs/<시각>/`(`summary.json`)를 가리킨다(`truth.py`는 바꾸지 않는다). I1 10회 = 배치 1~10을 한 번씩.
- **I1 판정**(`i1_summary(truth_dirs)`): 실행마다 `checks/*.json`에서 `status == "ok"`인 `result`를 정답 물체 가운데 가장 가까운 것(30mm 안, 벤치마크 `run_cycle`과 같음)과 짝짓고, 위치 15mm 이하 + `angle_ok`(정사각형은 위치만)를 성공으로 센다(1절 "성공" 정의. A1의 10mm와 다르다). 한 정답 물체에는 처음 짝지은 결과 하나만 센다. 인식 시간은 note의 `log=` 폴더 `summary.json`에서 그 실행의 모든 물체의 `radar_s + check_s`를 더한 값이고(벤치마크 "3개 끝까지" 인식 시간과 같은 뜻), 10회 평균을 100초와 비교한다(`summary.succeeded`는 놓은 물체 수라 쓰지 않는다). 합격은 1절 I1 기준: 10회 평균 2개 이상 성공, 인식 평균 100초 이하.

**`TruthRun` 만들기**: A1·I1 모두 `TruthRun("A1"|"I1", src.cfg, sim=a.sim, note=…)`(`radar_check.py`의 R1과 같음)이고, 소스를 만든 뒤 `src.record_dir = run.dir`로 넣는다. `service/ultrasonic.py`의 `make_ultrasonic_source`는 바꾸지 않는다(가상 `calibrate()`는 파일을 쓰지 않아 뒤에 넣어도 잃는 기록이 없다).

### 8.7 센서 오프셋 보정 도구 `checktest a0` (초안, 2026-11-20. 결정 0048 Stage 9 꼭 고칠 것 7건 반영)
10절 A0이다. 지름 10mm 막대 하나를 작업대 자리 S1 (189, 169)에 세우고, 같은 후보로 확인(CHECK)을 5번 돌린다. 확인 결과가 막대에서 어긋난 양으로 `arm_sensor_offset_mm`의 고칠 값을 낸다. A1 전에 한 번 하고, 브래킷을 다시 달거나 그리퍼를 바꾸면 다시 한다(3.3).

**원리**
- 팔은 `ArmService.sensor_position`에서 오프셋을 도구 축 `kin.tool_axes(q)`의 x·y열로 옮긴다(`arm_service.py:534`). 손끝이 수직 아래이고 손목 yaw가 ψ이면 손 x축 = (−cosψ, −sinψ), 손 y축 = (−sinψ, cosψ)다(`kinematics._rotation`). 아래를 보므로 회전이 아니라 거울(행렬식 −1)이다. 손 좌표의 축 뜻은 3.3과 `set_sensor_offset` 주석이다(x = 턱이 벌어지는 축).
- 실제 오프셋이 설정보다 δ = (δx, δy, δz) 다르면, 막대가 실제 센서 아래에 올 때 팔이 보고한 센서 위치는 막대에서 그만큼 비켜 있다. 막대 자리 p(정답), 확인 중심 c(결과 `x_mm`·`y_mm`)로 e = p − c = 손 x축·δx + 손 y축·δy다. u = (cosψ, sinψ), v = (−sinψ, cosψ)이면 손 x축·u = −1, 손 y축·v = 1, 나머지 내적은 0이라 **δx = −(e·u), δy = e·v**다. ψ는 아래 "인터페이스"의 값이다. `check.py`의 `sensor_to_tip`·`pick_yaw`도 #539로 같은 규약 R(yaw)·(−off.x, off.y)를 쓴다(결정 0075-3, 8.2). A0는 팔이 보고하는 `PoseSample.sensor_mm` 좌표계(위 식)를 따른다.
- 높이: 센서가 설정보다 δz 높으면 거리가 δz 길어져 물체 높이가 δz 작게 나온다(z = 손끝 z + `off.z`, 돌리지 않는다). 그래서 δz = 막대 높이 − 확인 결과 `height_mm`이다. 여기에는 손끝 높이 오차, `table_z_mm` CAD 오차, 음속(온도), 비스듬한 빔의 거리(실물만, 가상 `arm_echo`는 수직 거리만 쓴다)도 섞인다.
- δ에는 그 자리의 손끝 위치 오차(캘리브레이션·처짐)도 섞인다. A0은 둘을 나누지 않고 오프셋에 넣는다. 다른 자리·방향에서도 맞는지는 A1(세 자리, 반경 150~210)이 본다.

**명령**
```
so101.cmd --speed 30 checktest a0 --us-port COMx [--obj 10x10x40] [--note 메모]
so101.cmd --sim checktest a0
```
- `--obj` 기본은 하위 명령마다 정한다: a0 `10x10x40`(지름 10mm·높이 40mm 막대를 정사각형으로 본다), a1 `40x80x40`. 전역 기본은 None이고, CLI는 하위 명령별 기본을 높이 검사(`max_object_height_mm` 40)보다 먼저 정한다. a0에서 폭 ≠ 길이면 시작 전에 거부한다. 하위 명령 거부 문구("a0·a1뿐이다")와 `--obj` 도움말도 고친다. a0에 `--seed`·`--offset`·`--reps`가 오면 경고 한 줄을 찍고 무시한다.
- 5회 중 `empty`가 나오면 `--obj 20x20x40`처럼 굵은 막대로 다시 한다.
- 후보는 막대 자리 그대로(오프셋 0)인 `DetectedObject(f"a0-{n}", 189, 169, None, 0.0, 0.0, 0.3, "ultrasonic")`다. 180mm 직선(L1·L2)은 선 방향 오차를 덮는다. 선에 수직인 오차는 빔 반경 + 막대 반폭(빔 반각 7.5°에서 약 20mm) 안이어야 L1이 잡는다. 둘 다 비면 실패용 격자(100×100mm)가 찾는다. 잡히는지는 B1 빔 반경에 달렸다.
- 흐름: `run_a1`을 쓰고 아래 두 가지("인터페이스")만 바꾼다. 회마다 `radar_clear` → `place(item)` → `check_candidate` → `run.add`다. 기록은 `TruthRun("A0", src.cfg, sim=a.sim, note=a.note)`다.
- 정답은 `truth.obj(x, y, None, w, l, h, id="P1")`(`--obj` 값)이고, δz의 막대 높이는 `truth["height_mm"]`이다.
- a0의 `place`는 첫 회(n = 1)에만 묻는다: "막대를 S1 (189, 169)에 세우고 손을 뺀 뒤 Enter"(다르게 세웠으면 "x y" 두 값, `q` = 끝이면 None). 받은 `{**truth, x_mm, y_mm}`를 클로저에 저장하고, 2~5회는 묻지 않고 저장한 dict를 돌려준다. `--sim`은 첫 회에만 `src.esp.boxes = [Box(x, y, 0, w, l, h)]`를 넣는다.

**판정과 출력**(`a0_summary(res, cfg, origin)`)
- 5회 모두 `ok`여야 계산한다. 아니면 "미완료(ok 회 수/5)"이고 값을 내지 않는다.
- 회마다 δ를 구하고 성분별 중앙값을 낸다. 퍼짐(성분별 최대 − 최소)이 x나 y에서 4mm, 또는 z에서 6mm를 넘으면 "불안정"(막대·브래킷 흔들림, 메아리 끊김)이고 값을 내지 않는다.
- 안정이고 |중앙값 x|·|중앙값 y|가 각각 2mm 이하, |중앙값 z|가 3mm 이하이면 "합격: 지금 값 그대로"다. 아니면 "고칠 값"으로 새 오프셋(설정 + 중앙값, 0.1mm 반올림)을 `arm_sensor_offset_mm: {x: …, y: …, z: …}` 한 줄로 찍는다.
- 도구는 설정 파일을 쓰지 않는다. 사람(또는 초음파 세션)이 고칠 값을 `config/ultrasonic.yaml`에 넣고 `measurements.md`에 적는다. 넣은 뒤 다시 돌려 "합격"이면 A0이 끝나고 A1로 간다. 두 번째도 고칠 값이 나오면 값을 넣지 않고 A1을 돌린 뒤 두 결과를 총괄에 올린다("손 좌표 오프셋 하나"라는 가정이 안 맞을 수 있다).
- `--sim`의 가상 센서는 팔이 보고하는 `sensor_position`과 같은 값이라 δ ≈ 0은 구조상 당연하다. 식이 맞는지는 이것으로 보지 못하고 아래 단위 시험이 본다. 남는 것은 추정기 치우침이다(속도 100%·30Hz면 점 간격 약 3.3mm, `sample_mm` 6). 구현 PR은 `--sim` 5회의 δ 중앙값·퍼짐을 PR에 적는다. 2mm·4mm 기준을 넘으면 기준을 다시 정한다(총괄 승인).

**인터페이스**
```python
# service/check_test.py
A0_SPOT = ("S1", 189, 169)
A0_N = 5
def a0_plan(obj=(10, 10, 40)) -> list[dict]: ...                           # a1_plan과 같은 모양 5개, rep 1, cand = 막대 자리
def a0_offsets(res, cfg, origin) -> list[tuple[float, float, float]]: ...  # ok인 회마다 δ (위 식)
def a0_summary(res, cfg, origin) -> str: ...                               # 중앙값·퍼짐·판정·새 값 줄
```
- ψ = `pick_yaw(cfg, (cand.x_mm, cand.y_mm), origin)`(CHECK가 쓴 값, 정답 자리가 아니라 후보 자리)이고 5회 모두 같다(S1에서 약 100.6°). cfg = `src.cfg`, origin = `src.arm_origin`(`source.py`).
- `run_a1`에 `per_rep` 인자를 더한다(기본 `A1_N`, a0는 `A0_N`). 표시는 `n/per_rep`이다(`n`은 묶음마다 1부터라 `len(plan)`을 쓰면 `--reps 2`가 깨진다).
- 회별 dict에 결과 `x_mm`·`y_mm`·`height_mm`(ok가 아니면 None), `truth_xy`, `cand_xy`를 더한다.
- **고칠 파일(팔 세션)**: `cli/__init__.py`(`checktest a0` 분기, 하위 명령별 `--obj` 기본, 첫 회만 묻는 `place`, 거부 문구), `service/check_test.py`. 초음파 영역은 바꾸지 않는다(`pick_yaw`·`truth`는 가져다 쓴다).
- **시험** `tests/test_check_test.py`:
  - 단위(팔 좌표계와 식이 맞는지): `--sim` `ArmService`를 ψ = 100°·손끝 수직 아래 자세로 옮긴 q에서 `set_sensor_offset(o)`와 `set_sensor_offset(o + (3, −4, 2))`로 `sensor_position(q)` 차이 d를 얻는다. `a0_offsets`의 식에 e = −d를 넣어 (3, −4)를 1e-3mm 안으로 되찾는다. 같은 시험에서 fk yaw가 ψ와 1° 안인지도 본다(IK 자세 가중치 0.1).

  - 끝까지(`@pytest.mark.slow`, 8.6 틀): `--sim checktest a0`이 5회를 돌고 `truth.json`의 `placements` 5개·각 `checks` 1개이며 "합격"이다.

- **안전**: 8.6과 같다. 막대는 테이프나 점토로 세운다(쓰러지면 확인이 빈다). 확인 높이가 55mm라 손끝이 막대 끝 위 15mm를 지난다.

### 8.8 2차 추정기 준비: `--sim` 정답 쌍으로 길 먼저 짜기 (초안, 2026-11-20)
결정 0072 4항의 "스캔 → 위치·크기" 지도학습 추정기는 2차(12/4 뒤)다. 지금은 **데이터 읽기·학습·평가의 길만** `--sim` 정답 쌍으로 짜 둔다. 실물 R1·A1·I1 정답 쌍이 생기면 데이터만 바꾼다. 가상 ESP32 데이터로 학습한 모델은 가상 센서 모델을 배울 뿐이므로, 이 단계의 숫자로 성능을 말하지 않는다.

- **먼저 할 것은 팔 확인 추정기**다. 비교 실험 (가)에서 레이더 후보는 90mm 안 100%로 확인 경로가 찾기에 충분하다. 반면 확인 위치 90%는 비관 17~22mm로 목표 10mm를 넘는다(1절). 레이더 추정기는 R1 실측을 본 뒤 정한다.
- **입력**: `truth.pairs(run_dir)`(8.4)가 내는 (자리, scans, checks)다. 확인 하나가 표본 하나다.
  - 특징: `checks/NNN.json`의 `segments`에서 단계(L1·L2·R·L3·L4)별 점 (x, y, h)를 후보 중심·확인 yaw 기준 좌표로 옮긴 것(yaw는 기록에 없으므로 `truth.json`의 `config`로 `pick_yaw`를 다시 계산한다), 그리고 규칙 결과(중심, φ, R, 구간 길이, `cut`·`broken`).
  - 정답: 같은 자리의 가장 가까운 물체(`truth_report.check_rows`와 같은 짝짓기)의 중심 차이(후보 기준), 각도(180° 주기라 2φ의 cos·sin), 폭·길이.
  - 정답 물체가 30mm 안에 없는 확인과 `ok`가 아닌 확인은 뺀다.
- **`--sim` 데이터 만들기**: `so101.cmd --sim checktest a1 --reps 50 --seed K --obj <크기>`를 크기 셋(30×100·40×80·50×50)으로 돌린다. 12 × 50 × 3 = 1800 표본이다. 자리가 세 곳뿐이라 위치는 다양하지 않다. 후보 좌표계로 옮기므로 먼저 이것으로 길을 확인하고, 모자라면 `a1_plan`에 무작위 자리 옵션을 붙인다(그때 REQ). 낙관·비관 두 센서 모델로 따로 만든다(`truth.json`의 `config`에 남는다).
- **모델 후보**(고르기 전에 `researching-references`로 조사하고 사용자 승인을 받는다):
  1. 기준선: 지금 규칙(`check.py`). 이것을 못 이기면 쓰지 않는다.
  2. 규칙 결과 + 잔차 보정: 특징에서 (Δx, Δy, Δ각도)를 맞추는 선형·릿지 회귀(numpy만, 새 설치 없음). 실물 표본이 A1 묶음당 12개로 적을 때 맞는다.
  3. 그래디언트 부스팅 잔차 보정(scikit-learn, 새 설치라 승인이 필요하다).
  4. 점 묶음을 직접 받는 작은 신경망(PointNet 꼴, torch는 lerobot과 함께 이미 있다). 표본이 수천 개를 넘을 때만 본다.
- **평가**:
  - 나누기: 실행 폴더(`truth.json`) 단위로 나눈다. 같은 실행의 확인이 학습과 평가에 섞이지 않게 한다. 실물은 표본이 적으므로 실행 하나씩 빼고 돌린다(leave-one-run-out).
  - 값: A1과 같다. 위치 오차 중앙·90%·10mm 안 비율, `angle_ok` 정답률, 폭·길이 오차 중앙. 같은 평가 묶음에서 규칙과 나란히 낸다.
  - 채택 조건(초안): 평가 묶음에서 위치 90%가 규칙보다 낮고, 중앙값과 방향 정답률이 나빠지지 않는다.
- **자리(초음파 세션)**: `perception/ultrasonic/learn/`의 `dataset.py`(`truth.pairs` → 표, `index.jsonl`로 실행 고르기), `fit.py`, `evaluate.py`(`truth_report`의 짝짓기·`p90` 재사용). 작업 실행에 붙이는 설정(`check.estimator: rule|learned`)은 채택된 뒤에 정한다.
- 밖: 레이더 추정기, 작업 실행 연결, 실물 데이터 수집(R1·A1·I1이 남긴다).

### 8.9 작업 공간 인식 보여 주기: 소스·이벤트·멈춤 고리 (피드백 F2·F7, 2026-11-20, Stage 9 v3 반영: 구현 근거)
사용자 피드백 F2·F7(`feedback-1120-plan.md`)의 데이터 쪽이다. 화면은 `gui-spec.md` 12.11이다. GUI 작업 공간에서 실제 작업 실행(`TaskRunner`)이 초음파 소스로 돌 때 단계마다 무엇이 보였는지를 이벤트로 낸다. 인식 계산은 바꾸지 않고 이벤트 내기만 더한다. 예외 하나: 팔 지우기(`arm_links_fn`)를 빠짐없이 켜므로 첫 SCAN 결과가 지금과 조금 다를 수 있다.

**이름**
- 확인 단계(6절): L1·L2 직선, 원 단계(R), L3·L4 긴 축·짧은 축(기본 설정에서는 한 구간 `L34`, 도달 범위로 잘리면 `L3`·`L4`로 나뉜다), L1·L2가 다 비면 `GRID`(±50mm 격자).
- 1차 중심 = L1·L2(또는 `GRID`)로 정한 중심. φ = 원 단계가 정한 긴 축 각도. 방향 강도 `R`(0~1). `extent` = 직선 하나에서 메아리가 이어진 구간의 길이(`check.py`의 `hit["extent"]`).
- `src` = `backend.perception_source`. `_tell_known` = SCAN 뒤 찾은 물체를 팔 스킬(`Skills.known_objects`·`known_height`)에 알려 주는 러너 함수(`runner.py`).
- 흐름 단계(원 번호는 이것에만 쓴다): ① 레이더 회전·원자료 ② 거르기·예상 범위 ③ 팔 확인 ④ 좁히기·위치 ⑤ 집기. 초음파 화면의 겹은 이름으로 쓴다(바닥 원자료, 팔 원자료, 바닥 거른 데이터, 팔 후보별 원자료, 합치기, 최종 위치, `gui-spec.md` 12.11).

**소스 고르기**(GUI 백엔드, 실행 중이 아닐 때만)
- `backend.source`는 늘 `ManualSource`(정답 목록)다. `objects()`와 물체 편집 함수는 이것만 쓴다.
- 작업 소스는 `backend.perception_source`(`ManualSource` 또는 `UltrasonicSource`)다. 바꾼 뒤 `_make_studio()`를 부르고, `_make_studio()`는 `Studio(self.arm, self.perception_source, …)`로 만든다. 재연결 때도 같다.
- 고르기는 `backend.select_perception(kind)`(kind = `manual` | `us_sim` | `us_real`)이다. 페이지가 `await run.io_bound(backend.select_perception, kind)`로 부른다. 이벤트 루프에서 부르면 감시 heartbeat(0.2초마다, 끊김 한계 1초)가 끊긴다. `_dispatch`는 결과의 `.status`를 읽는 함수라 이 길에 쓰지 않는다.
- `select_perception`은 새 소스를 만들기 전에, 지금 `perception_source`가 `backend.source`가 아니면 `close()`한다(실물 소스는 `close()` 때까지 포트를 쥔다).
- 수동: `perception_source = backend.source`(지금과 같다).
- 초음파(가상):
  - `backend.real is None`일 때만 켠다. 실물 팔은 시작할 때 한 번 정해지므로 이 조건으로 충분하다.
  - 고르기 전에 "팔이 대기 자세(`radar_clear`)로 가고 기준값을 잽니다(기준값 3바퀴 약 4.4초 + 대기 자세 이동)" 확인 창을 띄운다.
  - 만드는 동안 `backend._us_building = True`다. `move_lock()`은 맨 앞(`real is None` 분기보다 먼저)에서 이것을 보고 "기준값 재는 중"을 돌려준다. 그래서 조그·작업 시작·스캔이 막힌다.
  - `make_ultrasonic_source(self.sim, sim=True, boxes=…)`. 이 함수는 `radar_clear().status != "ok"`이면 `RuntimeError`를 낸다(그 자리에서 기준값을 재지 않는다). 예외가 나면 소스를 버리고 수동으로 돌아가며 이유를 알린다.
  - 시계: `make_ultrasonic_source`는 `RealClock()` 대신 `arm.clock`을 `FakeESP32`·`Link`에 넣는다. 팔 자세 기록(`PoseTrail`)이 팔 시계로 남으므로 레이더도 같은 시계를 써야 한다. 시계 인자는 두지 않는다.
  - 팔 지우기: `make_ultrasonic_source`는 소스를 `arm_links_fn=trail.links_at`으로 만든다. 지금은 `prefetch()` 안에서만 채워져, prefetch를 끄면 레이더가 팔 메아리를 지우지 못한다.
  - Box 변환은 `demo_boxes`(`ultrasonic_view.py`)에 높이 `o.height_mm or 40`을 더해 함께 쓰고, 목록은 복사해 넘긴다.
  - `src.esp.boxes`는 소스를 만들 때와 사용자가 정답 목록을 고칠 때만 다시 채운다. `start_task` 직전에는 채우지 않는다(집혀 빠진 물체가 되살아난다). 처음 배치로 돌리려면 정답 목록을 고치거나 소스를 다시 고른다.
- 초음파(실물):
  - `board.connected`가 참이고 `board.port != SIM_PORT`일 때 켜진다(`board = board_of(backend)`, `Board.port`는 끊겨도 비워지지 않으므로 `connected`를 본다). 고르면 포트 이름을 받아 둔 뒤 `board.disconnect()`를 부르고, 그 포트로 `make_ultrasonic_source(arm, sim=False, port=…)`를 연다.
  - 초음파(실물)가 작업 소스인 동안 ESP32 페이지의 [연결]을 끄고 "작업 공간 초음파(실물)가 사용 중"이라고 보인다.
  - 실물 소스는 만든 직후 `baseline`이 None이다. 고를 때 `config/ultrasonic_baseline.json`이 없으면 막고 "기준값 파일이 없습니다. 빈 작업대에서 팔을 대기 자세(`radar_clear`)에 두고 `python -m so101_studio.perception.ultrasonic.radar_check --port <포트> calibrate`로 잽니다"를 띄운다. GUI의 실물 기준값 버튼은 이번에 만들지 않는다. 있으면 `src.baseline = radar.Baseline.load(src.baseline_path)`로 읽어 둔다.
  - 팔 지우기: `_begin_checkable`은 새 `PoseTrail`을 만든 뒤 늘 `self.source._links_fn = self._trail.links_at`을 넣는다(실물 팔에는 `arm.trail`이 없어 실행마다 새 기록이 생기므로, 조건을 달면 두 번째 실행부터 끝난 기록으로 지운다). 가상 소스는 `arm.trail`과 같은 객체라 결과가 같다.

**이벤트**(`Studio.bus`, 화면은 이것만 보고 그린다)

| 이벤트 | 있음/새로 | 내는 곳 | 내용 | 쓰는 곳(3D 단계 / 화면 겹) |
|---|---|---|---|---|
| `us.sweep_progress` | 새로 | `source.py` `_service()` | 아래 규칙 | 3D ① 머리 각도·빔·메아리 점 / 바닥 원자료 |
| `us.sweep` | 있음 | `source.py` | 한 방향 회전마다 `{pass, dir, t_ns, angles, d}` | 3D ① / 바닥 원자료 |
| `us.candidates` | 있음(필드 추가) | `source.py` `scan()`·`rescan()` | 후보마다 `search_r_mm`, 이벤트에 `values` | 3D ② / 바닥 거른 데이터 |
| `us.check_path` | 있음 | `check.py` | `{id, stage, phase, points_mm, tool_z_mm, points(x, y, h), unreachable}` | 3D ③ / 팔 원자료·팔 후보별 원자료 |
| `us.check_estimate` | 새로 | `check.py` `_run` | 단계가 끝날 때마다 하나. 필드는 아래 표 | 3D ④ / 합치기 |
| `us.check_result` | 있음 | `source.py` | 최종 결과·상태 | 3D ④ / 최종 위치 |

- `us.candidates`의 후보는 `{**asdict(o), "search_r_mm": cfg.check.line_mm / 2}`다. `search_r_mm`은 첫 십자 직선이 닿는 반경이다. 이 원 안이라고 늘 찾지는 않는다(두 직선만 지나므로 대각선 쪽 작은 물체는 비켜 갈 수 있다).
- `values`는 `{각도(°): 합친 거리(mm)}` dict다(`raw["values"]`, 없으면 None).

`us.check_estimate` 필드(이름은 이것으로 확정한다. 바꿀 때는 초음파 세션이 이 표와 `gui-spec.md` 12.11을 함께 고친다):

| `stage` | `center` | `angle_deg` | `strength` | `size_mm` | `spread_mm` |
|---|---|---|---|---|---|
| `L1` | L1 중심(없으면 후보) | None | None | None | L1 `extent`/2(없으면 `line_mm`/2) |
| `L2` | L2 중심 또는 1차 중심 | None | None | None | 있는 `extent` 중 큰 값/2(둘 다 없으면 `line_mm`/2, 이어서 `GRID`) |
| `GRID` | 격자 중심 | None | None | None | 50 |
| `R` | 1차 중심 | φ(R ≤ 0.3이면 None) | R | None | 직전 행(L2 또는 GRID)의 값 |
| `L34`(나뉘면 `L4`. `L3` 뒤에는 내지 않는다) | 최종 중심(= 결과 `x_mm`·`y_mm`) | 최종 각도 | R | (길이, 폭) | 0 |
| `none`(오검출, `_run`이 None) | None | None | None | None | None |

- 모든 행에 `id`(후보 id, `us.check_path`의 `id`와 같다)와 위 열이 늘 있다. 값이 없으면 키를 빼지 않고 None을 넣는다. `center`는 `(x_mm, y_mm)`이다.
- 후보 단계 값은 이벤트로 내지 않는다. 화면은 `us.candidates`의 `search_r_mm`을 쓴다. 최종 중심은 L3·L4를 다 받은 뒤에 셈하므로 `L3`만 끝났을 때는 낼 값이 없다.
- 화면 쪽 `on_event`는 예외를 내지 않는다(`EventBus.publish`는 콜백 예외를 작업 스레드로 올린다).

**`us.sweep_progress` 규칙**
- `_service()`가 `r` 줄을 받을 때, `self.clock.now_ns()`로 보아 마지막으로 낸 뒤 100ms를 넘었으면 그 사이 새 값만 낸다: `{pass, total, dir, servo_deg, t_ns, angles[], d[]}`.
- `pass`는 바퀴 번호다. 빈 작업대라 3바퀴를 더 돌면 1부터 다시 센다.
- `total`은 `_start_sweep(n)`의 n이다. `self._total`에 두어 prefetch 바퀴도 센다. `early_start`가 켜져 있어 보통 1바퀴, 비면 3바퀴 더, RESCAN은 4바퀴다.
- `dir`: `_start_sweep` 뒤 첫 바퀴는 +1이고, `end`마다 `bounce`면 부호를 바꾸고 아니면 +1이다(ESP32 `r` 줄에는 방향이 없다).
- `servo_deg`는 마지막 `r`의 `ang`(실제 각도), 없으면 명령 `a`다. 기본 `driver: pwm`이라 보통 `a`다. `t_ns`는 마지막 `r`의 시각이다.
- `end`를 받으면 남은 값을 먼저 낸 뒤 `us.sweep`을 낸다. 기록(`scans/`)은 바꾸지 않는다.

**멈춤 고리**(팔 세션 `task/runner.py`, 초음파 세션 `perception/base.py`·`check.py`)
- `TaskRunner.pace: Callable[[str, str | None], None]`(단계, 확인 단계 이름). 기본은 아무것도 하지 않는다.
- 단계 이름: `PathSegment`에 `stage: str | None = None`을 더하고 `Probe._seg_of`가 채운다. 잘린 조각과 당겨 다시 내기(`retry_pull_mm`)는 같은 이름으로 다시 나간다. `checks/` 기록에도 `stage`가 생긴다.
- 부르는 곳:
  - `"scan"`: SCAN의 `scan()`·`_tell_known` 뒤와 `rescan()` 뒤.
  - `"check"`: `_check`는 지역 변수 `last`(처음 None)를 두고, `seg.stage`가 `last`와 다를 때만 `follow_path` 바로 앞에서 `pace("check", seg.stage)`를 부른다(후보의 첫 구간은 늘 부른다. 단계당 한 번). 돌아온 뒤 `if self._stop or self.arm.ctl.state in ("stopped", "fault"): probe.abort(); return None, "aborted"`.
  - `"check_done"`: CHECK 결과 뒤.
  - `"pick"`: `_emit("PICK")`과 `_stopped()` 사이(기다리는 동안 누른 정지를 집기 전에 본다).
  - `check_candidate`·`_recheck_height` 경로도 `_check`를 거치므로 같이 불린다.
- 이벤트 순서: 다음 구간의 `us.check_path` phase=`start`는 `Probe.feed()`가 내므로 `pace("check")`보다 먼저 온다. 화면은 이것으로 다음 단계 이름을 캡션에 띄운다. phase=`end`와 팔 이동은 `pace` 뒤다.
- 기다리기: 고리는 GUI 세션(`gui/backend.py`)이 만드는 `pace`다. runner는 부르기만 한다.
  - 들어올 때 `Studio._step.clear()`를 한다(팔이 움직이는 동안 누른 [다음]이 남아 다음 `pace`를 그냥 지나가지 않게).
  - 0.1초마다 `task._stop`, `arm.ctl.state in ("stopped", "fault")`, `backend.paused`를 다시 읽는다. 앞의 둘 중 하나면 바로 돌아온다. `time.sleep`은 쓰지 않는다.
  - `paused`가 참이면 `_step.wait(0.1)`이 참이 될 때 돌아온다([다음] 대기).
  - 거짓이면 들어온 뒤 `EXPLAIN_PAUSE_S`(2초)가 지나면 돌아온다.
  - 감시 프로세스의 정지(`StopListener` → `arm.estop()`)도 이렇게 풀린다. 정지 처리는 그대로다: GUI 정지는 STOPPED, 감시 정지는 FAULT로 끝난다.
- `pace`는 `source.scan()` 안에서 부르지 않는다(바퀴 중간에는 쉬지 않는다).
- GUI가 넣는 것(`gui-spec.md` 12.11 "모드"): `TaskRunner`는 Studio를 만들 때 한 번만 생기므로 `start_task`가 실행마다 두 값을 다시 넣는다.
  - 빠른 모드: `task.pace` = 아무것도 하지 않는 함수, `task.prefetch_enabled = True`. 빠른 모드의 단계 실행([한 단계])은 지금처럼 `step_mode=True`다.
  - 설명 모드: `task.pace` = 위 고리, `task.prefetch_enabled = False`, `studio.start(step_mode=False)`. 설명 모드의 `toggle_pause`는 `backend.paused`만 뒤집고 `studio.pause()`·`resume()`을 부르지 않는다(`step_mode`가 다시 켜져 `pace`와 겹친다).
- **prefetch**: `TaskRunner.prefetch_enabled = False`면 PLACE에서 `prefetch`를 부르지 않는다. 그래야 다음 SCAN이 실시간으로 돈다. 빠른 모드는 지금 그대로이고, 미리 돈 바퀴는 다음 `scan()` 때 몰아서 온다(PLACE 동안 아무도 `_service()`를 부르지 않기 때문이다).

**레이더 머리**(팔 세션)
- `radar_station.stl`(바이너리)은 면마다 꼭짓점이 따로라 `split()`이 2473조각을 낸다(쓸 수 없다). 꼭짓점을 합치면(`merge_vertices(digits_vertex=2)`) 연결 성분이 14개다(2026-11-20 총괄 trimesh 실측, 원점 = 서보 축, mm). 원본 CAD 바디 27개와 1:1이 아니다(볼록 껍질끼리 붙음).
- 나누기 규칙(변환 스크립트에 고정): 머리 = 성분 12(센서 브래킷으로 보임, x −24.5~24.5, y −38.5~8.2, z 11.2~35.2)와 성분 13(HC-SR04 둘로 보임, y −48.7~−31.8, z 13.2~39.3), 그리고 bounds가 z 11mm 이상이면서 xy가 12·13의 xy 상자를 합친 안에 다 들어가는 성분(나사·스페이서). 받침 = 나머지(몸체 상자 0, XL330으로 보이는 5 등).
- 스크립트는 성분마다 번호·bounds·꼭짓점 수와 머리/받침 판정을 표로 출력한다. 성분 수가 14가 아니거나 12·13의 bounds가 위 값과 1mm 넘게 다르면 멈춘다. 그때는 팔 세션이 받아 둔 원본 CAD에서 머리 바디(센서 브래킷·HC-SR04·나사)와 받침 바디를 따로 같은 변환(x = −z_cad, y = 380 − x_cad, z = y_cad + 1, 바디마다 볼록 껍질)으로 내보내고, 이어서 서보 축 (207.3, 405.5, 0)을 빼 원점으로 둔다(NOTICE 5행과 같다). 그동안 `radar_station.stl` 하나로 두고 머리는 돌리지 않는다.
- 결과는 `radar_base.stl`·`radar_head.stl`이고 `radar_station.stl`을 지운다. shortcut: 서보 혼(성분 6일 수 있음)의 판정은 규칙대로 둔다. 모양만 보이는 것이라 틀려도 그대로 둔다.
- `core/scene.py`의 `ScenePart`에 `spin: str | None`을 더하고 `load_scene`이 읽는다. `config/scene.yaml`의 머리 부품에 `spin: radar`를 단다.
- GUI `set_parts`는 `getattr(part, "spin", None)`으로 읽고(시험이 `spin` 없는 객체를 넘긴다) spin 부품 핸들을 따로 둔다. wxyz를 z축 (`servo_deg` − 90)°로 바꾼다(위에서 보아 반시계가 +, `radar.py`와 같다). 충돌 검사는 정면(90°) 형상 하나만 쓴다(`scene.yaml` 주석의 shortcut 그대로). MuJoCo는 `radar_head`를 정면 고정 body로 두고 `spin`을 무시한다.
- `radar_station`을 단정하는 시험 네 곳을 고친다: `tests/test_scene.py` 두 곳(이름과 bounds를 두 부품을 합친 값으로), `tests/test_scene_collision.py`, `tests/test_mujoco_model.py`(MuJoCo 세션에 알림).

## 11. 정할 것과 열린 질문
- 스캔 서보는 OpenRB-150 + XL330(결정 0043)이다. 서보 전원은 5V(A 충전기 또는 B 강압 모듈, 결정 0043-2)이고 12V를 OpenRB VIN에 넣지 않는다. 손목 브래킷은 결정 0063이다(0035는 대체됨).
- `check.tool_reach_mm`은 그리퍼별이다(1절: H-2 뒤 병렬 95~230, 단동식 100~255, REQ-090·091). `table_z_mm`이 CAD 값이라 작업대 실측(H-6)과 실물 A0 뒤 같은 계산으로 다시 정한다.
- 모드는 하나로 정했다(결정 0038). T8은 옵션이다.
- 초음파 세션은 결정 0036으로 만든다(Sonnet, 폴더 `../so101-studio-us`).
- 도달 범위는 6절 "도달 범위로 자르기"로 정했다(U3 결과). 실물에서 바깥쪽이 더 모자라면 센서를 손끝 바깥쪽에 다는 브래킷(센서 도달 최대 약 30mm 증가, 턱 간섭 확인 필요)을 검토한다.
- 레이더 시야에 팔 받침이 들어오는 영향은 기준값에 포함된다고 보고, R1에서 확인한다.
- **R1 자리 (280, 150)과 통**(2026-11-20 기획 판단): 옮기지 않는다. R1은 무시 구역 없이 레이더 정확도를 재는 시험이고, 기준값에 통이 들어가므로(10절 R1: 통을 제자리에 두고 기준값을 잰다) 이 자리는 통 벽 바로 옆 물체를 레이더가 가를 수 있는지 보는 값이 된다. 그 값으로 통 무시 반경(지금 반 대각선 + 벽 높이 + 여유 = 112.8mm, `ignore_zones`)을 줄일 수 있는지 본다. 작업 실행에서는 그 자리 물체가 가려지므로 A1·I1의 자리는 6절 시연 배치 규칙(물체 중심이 통 무시 원 112.8mm 밖, 몸체가 판 안이고 통 벽과 안 겹침, 벤치마크 `on_plate`와 같음. 50mm를 더 두지 않는다)으로 고른다(8.6).
