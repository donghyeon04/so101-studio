  - 앞서 "placo가 멈춘다"고 적었던 것(`spread90` 비관 씨앗 7, `single` 끔의 최대 300초)의 원인은 placo가 아니라 `arm/trajectory.py` 경로 계획 버그다(첫 구간이 1mm 이하면 계획 시간이 비정상으로 커짐, REQ-066). 실제 팔의 `follow_path`도 같은 함수를 썼고 #392로 고쳤다(계획 시간이 비정상이면 움직이기 전에 `plan_too_slow`로 실패). 벤치마크의 임시 우회는 #399가 지웠다.
- **2026-11-14 성능 저하**: 로보나인 + 짧은 브래킷(결정 0063)으로 센서가 작업대 위 약 154.5mm(전 설계 110mm)가 되어 같은 빔 반각에서 바닥의 빔이 넓어졌다. 벤치마크 `single` 비관 성공 78% → 62%, 3개 인식 기준을 130초로 완화했다. 빔 반각은 B1 실측 전 가정값이라, B1 뒤 다시 낸다. CHECK 높이·경로를 새 높이에 맞춰 다시 고르는 것은 초음파 세션 일이다(시험장 M6에서도 본다). 이 표의 숫자는 결정 0037대로 벤치마크 고정 시나리오와 커밋을 출처로 적는다.

"성공"은 위치 오차 15mm 이내이면서 방향이 맞은 물체 수다(정사각형 물체는 위치만). 1절의 가상 값은 2026-11-06 공식 표다. 앞 표(835a180, 평균 63~65초)보다 시간이 약 25초 긴 것은 가상 팔이 실제 팔 궤적 코드를 쓰게 되어서다: 접선·구심 가속을 함께 `tool_a_max`/√2(약 85mm/s²)로 묶고, 모서리를 2.5mm로 깎아 천천히 지나며, 180° 되돌아감에서 선다. 경로 길이와 횟수는 같고 평균 속도만 65→43mm/s로 떨어졌다. 성공률과 정확도는 씨앗 잡음(약 ±5%p) 안에서 같다. B1·B2 실측이 들어오면 벤치마크 모델 값을 고쳐 다시 낸다(결정 0037). T8은 비관에서 −7~+3%p로 이득이 일관되지 않아 기본 끔을 유지하고 U9에서 비교한다. "인식 시간"은 레이더와 팔 확인 시간의 합이고, 팔이 집고 놓는 시간은 뺀다.

## 2. 전체 흐름
```
 IDLE ─▶ PREPARE ─▶ SCAN ─▶ DECIDE ─후보 있음─▶ CHECK ─확정─▶ PICK ─▶ PLACE ─┐
    (radar_clear)   (레이더)    │                  │                        │
                                │                  └─확인 실패─▶ DECIDE      │
                                └─후보 없음─▶ RESCAN ─후보 있음─▶ DECIDE    │
                                              └─또 없음─▶ DONE              │
                     SCAN ◀──── (놓는 동안 레이더가 미리 돌려 둔 결과) ◀──────┘
```
- `SCAN`: 레이더가 후보 목록을 낸다. 후보는 `angle_deg=None`, `confidence` 0.3 이하인 `DetectedObject`다.
- `DECIDE`: 기존 규칙(도달 범위 안, 팔에서 가까운 순)으로 후보 하나를 고른다.
- `RESCAN`(새 상태): 후보가 없으면 바로 끝내지 않고, 팔을 레이더 시야를 가리지 않는 대기 자세 `radar_clear`(`PREPARE`와 같은 자세, 결정 0039: 링크 점이 모두 작업대 y 120mm 이하, 손끝 높이 150mm 이상. 기본값은 결정 0041의 위로 세운 자세 `[0, -90, 85, -90, 0, 3]`, 손끝 (300, 95.8) 높이 약 321mm)로 옮긴 뒤 레이더를 4바퀴 돌려 한 번 더 찾는다. 팔이 시야를 가려 남은 물체를 놓치는 경우를 막는다. 후보가 없을 때마다 한 번씩 하고, 연달아 두 번은 하지 않는다. 설정 `radar.rescan_home`(기본 켬). 근거: 8.5절 벤치마크(커밋 2078533, 씨앗 20개)에서 성공 +4~9%p, 인식 시간 +7~10초.
- `CHECK`(새 상태): 팔이 후보 위를 지나가며 손목 센서로 재서 중심·방향·크기를 확정한다(6절). 물체가 없으면 그 후보를 지우고 `DECIDE`로 돌아간다.
- `PICK`·`PLACE`: 그대로. `PLACE` 동안 레이더가 다음 후보를 미리 찾아 둔다(4절 T5). 그래서 두 번째 물체부터는 `SCAN`이 기다리지 않는다.
- **`radar_clear`를 거치는 때 (2026-11-06)**: 작업 실행의 첫 사이클(`IDLE → PREPARE`), `RESCAN`, 집기 실패 뒤 `PREPARE`뿐이다. `PLACE` 뒤에는 `PREPARE`를 거치지 않고 미리 돌린 결과로 바로 `SCAN`한다. 사이클마다 위로 올라갔다 내려오는 이동(약 270mm × 2)이 없어진다. 벤치마크(demo 씨앗 20, `radar_clear` [0,-90,85,-90,0,3])에서 PLACE 뒤에도 거치게 하면 낙관 100→98%, 비관 78→72%로 나아지지 않았다(씨앗 잡음 ±5%p 끝). 벤치마크도 같은 흐름으로 잰다: 첫 `SCAN` 전과 `RESCAN` 때만 `radar_clear`로 가고, 올라가는 이동은 인식 시간 밖, 내려오는 이동은 안에 넣는다.
- 다른 인식 방식(`ManualSource`, 카메라)은 `CHECK`를 건너뛴다. 인식 방식이 확인 기능을 가졌는지로 정한다(8.2절).

시간 흐름 예 (물체 3개, T8 옵션을 켠 경우):

| 시각(초) | 레이더 | 팔 |
|---|---|---|
| 0~1.4 | 한 방향 회전, 후보 발견 | 대기 |
| 1.4~ | 돌아오는 회전 계속(팔 자리는 지움) | 후보로 출발, 가는 길이 첫 확인선 |
| ~7 | 멈춤(팔 센서 우선) | 확인 끝 → 집기 → 놓기 |
| 놓는 동안 | 4바퀴 돌려 합침 | 배출 구역 |
| 다음 | 결과 준비됨 | 다음 후보로 바로 출발 |

### 3.2 스캔 서보 (결정 0043: OpenRB-150 + DYNAMIXEL XL330-M288-T)
레이더는 대략 위치만 구하고 정확한 값은 팔 확인이 구한다. 각도 정밀도는 ±3° 정도면 충분하다(30cm에서 약 1.6cm, 확인 경로는 ±9cm를 덮는다). 서보를 MG90S(PWM)에서 XL330으로 바꾼 이유는 성공률이 아니다(가상 시뮬레이션 차이가 ±5%p 안, #144). 이유는 두 가지다: 해상도 0.088°(4096/회전)와 **실제 각도 피드백**이다. 펌웨어는 측정 직전에 읽은 각도를 샘플의 `ang`로 보내고, PC는 후보 방위를 명령 각도 대신 이 값으로 고친다(7절, 서보 지연 ±3° 보정이 필요 없어진다). 지연·떨림은 B4 실측으로 확인한다.

### 3.4 ESP32 배선과 전원
팔 쪽(PC ─USB─ Seeed 모터 보드 ─ 팔 서보 6개, 12V 5A 어댑터)은 그대로 둔다. ESP32를 PC에 USB로 하나 더 꽂는다. PC에서는 COM 포트가 두 개가 된다.

```
PC ─USB(데이터)─ ESP32 ─┬─ 레이더 HC-SR04  TRIG 25, ECHO 26 (분압)
  (팔 받침 옆에 고정)    ├─ 팔 HC-SR04     TRIG 32, ECHO 33 (분압) ─ 1.5m 케이블로 손목까지
                         └─ 레이더 서보 (driver에 따라)
                              pwm: MG90S 신호 GPIO 13 ─ 60cm 연장선
                              dxl: UART2 GPIO 17(TX)→OpenRB Serial2 RX, GPIO 16(RX)←OpenRB Serial2 TX, GND 공통 ─ OpenRB-150 ─ XL330
HC-SR04 2개 전원: ESP32 5V(VIN) 핀 (개당 약 15mA)
서보 전원: 아래 A 또는 B. 모든 GND는 하나로 묶음
```

| 연결 | ESP32 핀 | 비고 |
|---|---|---|
| 레이더 TRIG | GPIO 25 | |
| 레이더 ECHO | GPIO 26 | 분압 1kΩ/2kΩ로 5V → 3.3V |
| 팔 센서 TRIG | GPIO 32 | |
| 팔 센서 ECHO | GPIO 33 | 분압 1kΩ/2kΩ |
| 서보 신호 (pwm) | GPIO 13 | LEDC PWM 50Hz |
| OpenRB 연결 (dxl) | GPIO 17 = UART2 TX, GPIO 16 = UART2 RX | 115200bps, 3.3V ↔ 3.3V(분압 필요 없음), TX/RX 교차, GND 공통. OpenRB 쪽은 Serial2 단자(2mm 1x4 핀 헤더 소켓 납땜 필요, 사용자 보고) |

**XL330 전원은 5V다(결정 0043).** 입력 범위가 3.7~6.0V라 **12V를 OpenRB VIN에 넣으면 XL330이 망가진다.** 배선 전에 OpenRB VIN 단자 전압을 멀티미터로 확인한다(사용자 결정 대기 U4, `work-queue.md`). OpenRB의 DXL 포트 전원은 VIN(전원 점퍼를 VIN(DXL) 쪽)에서 오고 FET가 꺼진 채 켜지므로 펌웨어가 핀 31을 켠다. USB-C만으로는 500mA 퓨즈라 정지 토크 1.47A를 못 받는다. 전류는 움직이기 시작할 때 최대 약 1.5A라 5V 2A 이상을 쓴다(MG90S는 0.5~0.8A였다). ESP32의 5V 핀에서 쓰지 않는다(리셋되면 센서 통신이 끊겨 작업이 멈춘다).

| 방법 | 구성 | 판단 |
|---|---|---|
| A. USB 5V 충전기 | 5V 3A 충전기 → USB-A 단자 보드 → OpenRB VIN 단자(점퍼 VIN(DXL)). 충전기 GND와 ESP32 GND 연결. 단자에 470µF. (pwm이면 서보 빨강·갈색에 직접, 신호는 GPIO 13) | 팔 전원과 완전히 분리. 팔 전원 사건(서보 6개 동시 토크 꺼짐 3회) 원인을 찾기 전에는 진단이 섞이지 않는다 |
| **B. 기존 12V 5A 어댑터 공유 (강압 모듈 방식은 0035에서 왔고, 지금 근거는 결정 0043-2)** | 어댑터 출력을 DC Y 분배 케이블로 나눠 한쪽은 모터 보드, 한쪽은 12V→5V 강압 모듈(3A급, 출력 5.0V로 맞춤, **멀티미터로 5.0V 확인한 뒤** 연결) → OpenRB VIN 단자. GND 공통, 470µF | 전기적으로 충분하다. 팔 최대 1.7A(powertest) + 서보 최대 약 1.5A×5V/12V ≈ 0.6A(12V 기준) = 약 2.3A로 5A의 약 46%. 다만 팔의 과전류 감시(4A)는 팔 서보 전류만 재므로 이 부하를 모르고, 어댑터 보호가 걸리면 레이더도 같이 꺼진다. 모터 보드의 남는 서보 포트에서 12V를 따지 않는다 |

- 출력 설정은 A1 README 권장대로 채움 40%, 트리 서포트(흔들림 방지).

## 4. 시간 줄이기 기법
가상 센서로 처음 판(레이더가 각도마다 멈춰 5회 측정, 팔은 14cm 사각 격자) 118~128초에서 시작했다.

| # | 기법 | 하는 곳 | 효과 (가상 센서) | 기본값 (결정 0038: 모드 하나) |
|---|---|---|---|---|

## 5. 레이더 처리 (`radar.py`)
1. **기준값(C1)**: 빈 작업대에서 3바퀴(정방향·역방향·정방향)를 돌려 각도별 중앙값을 저장한다. 바퀴 사이 차이가 20mm를 넘는 각도는 "불안정"으로 표시하고 후보에서 뺀다. 저장: `runs/<시각>/scans/baseline.json`, 최근 값은 `config/ultrasonic_baseline.json`(git 제외).
2. **바퀴 합치기**: 각도별로 그 판단에 쓸 바퀴 값(처음엔 1~2바퀴, 놓는 동안엔 4바퀴)의 중앙값. 응답 없음은 빼고 센다. 처음 1~2바퀴로 후보가 없으면 바로 끝내지 않고 `radar.empty_extra_sweeps`(기본 3)바퀴를 더 돌려 합친 값으로 다시 판단한다. 근거: 8.5절 벤치마크 비관 `single` 51→74%(커밋 fa7c409).
3. **후보**: 기준값보다 30mm(`dip_mm`) 이상 가까운 각도가 2개 이상 이어지면 호 하나. 거리가 25mm 넘게 바뀌면 다른 호로 자른다. 붙어 있는 호(각도 이웃, 대표점 사이 110mm 이하)는 한 물체로 합친다. 대표점은 호들의 (각도 중앙, 거리 중앙값) 평균이고, 후보 위치 = 대표점 + 센서 방향으로 15mm.
4. **팔 지우기**: 그 측정 시각의 팔 관절값으로 링크 점(어깨, 팔꿈치, 손목, 손끝)의 작업대 xy를 구한다. 그 점의 방위 ±(빔 반각 + 5°) 안이면서 거리 차가 60mm 안인 측정은 버린다.
5. **도달 범위**: 후보가 `workspace.yaml`의 `reach_mm` 밖이면 표시만 하고 고르지 않는다. 단, **확인 전 레이더 후보는 집는 범위(`pick_reach_mm`)보다 바깥으로 60mm 여유를 두고 거른다**(2026-11-15, REQ-065). 레이더 후보는 물체의 레이더 쪽 면(팔에서 먼 쪽)으로 치우쳐 반경이 크게 나온다(참값 222mm → 후보 260mm 사례, 후보 오차 90%가 56~63mm). 여유 없이 거르면 집을 수 있는 물체가 CHECK 전에 빠져 `no_objects`로 끝난다. 여유는 설정 키로 두고(이름은 코드가 기준), 확인 뒤 확정된 물체와 수동 입력 물체는 지금처럼 `pick_reach_mm` 그대로 거른다(집는 범위는 넓히지 않는다). 확정 위치가 집는 범위 밖이면 집지 않고 그 후보를 건너뛴다. 여유는 `config/workspace.yaml`의 `candidate_reach_margin_mm`(60)이고 최대 반경에만 더한다(최소는 그대로). 벤치마크(8.5절)도 같은 정책 함수(`policy.choose(unconfirmed=True)`)로 후보를 거른다(#391).
6. **출력**: `ScanResult.objects`에 후보(`angle_deg=None`, 폭·길이 0, `confidence` 0.1~0.3), `raw`에 각도별 바퀴 값·기준값·호·지운 각도.

## 6. 팔 확인 처리 (`check.py`)
손끝 높이는 3.3절 확인 높이로 고정, 손끝은 수직 아래다. **손목 yaw는 후보마다 한 값으로 정한다(결정 0065)**: 후보의 반경 r(팔 원점 기준)에서 센서가 손끝보다 바깥(반경 방향)으로 나가는 양이 c = clamp(r − `check.yaw_pivot_mm`(150), ±센서 옆 오프셋 66.5mm)이 되는 yaw다. 가까운 후보는 센서가 손끝 안쪽, 먼 후보는 바깥쪽에 와서 손끝 반경이 r − c(반경 100에서 150, 240에서 173.5)로 도달 범위 가운데에 머문다. 센서가 지나가는 선은 아래 표 그대로이고, 그 후보의 L1~L4·원 동안 yaw는 바꾸지 않는다. 조건을 만족하는 yaw 해는 둘이고 `check.yaw_deg`(90)에 가까운 쪽을 쓴다(손목이 덜 돈다). 옵션을 끄면(`yaw_pivot_mm`이 0이거나 없음) 전처럼 `yaw_deg` 고정이다. 센서 값 `h = 센서 높이 − 거리`가 15mm 넘으면 "물체 위"다. 측정은 30Hz, 팔 100mm/s에서 약 3.3mm마다 한 번.

| 단계 | 경로 | 얻는 것 |
|---|---|---|
| L1 | 후보를 지나는 길이 180mm 직선. 작업대 x축 방향. 옵션 `check.approach_line`을 켜면 팔 원점에서 후보로 가는 방향(접근 경로 겸용, T8) | 그 방향 중심 |
| L2 | L1 중심을 지나는 수직 직선 180mm | 다른 방향 중심 → 1차 중심 |
| R | 1차 중심 둘레 반지름 60mm 원(`check.ring_r_mm`, 센서가 높아져 2026-11-14 #359에서 45 → 60), 36점 | 물체가 걸리는 방향들 → 긴 축 각도 φ(두 배 각도 평균), 강도 R |
| L3 | 중심을 지나는 φ 방향 직선 180mm | 긴 축 방향 중심과 길이 |
| L4 | 같은 중심을 지나는 φ+90° 직선 180mm. L3와 한 번의 `follow_path`로 이어서 간다 | 짧은 축 중심과 폭 → 최종 중심(L3·L4의 치우침을 함께 더함) |

- 각 직선은 후보 중심(0)을 품거나 가장 가까운 메아리 구간을 고른다. 중간의 응답 없음 1칸은 이어 본다. T9(중심을 지난 구간이 끝나고 3칸 비면 멈춤)는 지금 끈다(4절).
- **방향**: R > 0.3이면 `angle_deg = φ`(0~180, 연속값). 비교 실험에서는 가까운 0/45/90/135°로 묶는다. R ≤ 0.3이면 정사각형·원형으로 보고 `angle_deg=None`, 집기는 기본 각도로 한다.
- **크기**: L3·L4 구간 길이 − 2 × 빔 반경. 빔 반경 = (센서 높이 − 물체 높이) × tan(빔 반각), 빔 반각은 B1 실측값(그 전에는 7.5°).
- **물체 높이**: 구간 안 `h`의 중앙값. `raw`에 남긴다(집는 높이 참고용).
- **신뢰도**: 0.5 + 0.5 × min(R, 1), 구간이 끊겼거나 L3·L4 중심 차이가 10mm를 넘으면 0.2를 뺀다.
- **도달 범위로 자르기**: 확인 경로(L1~L4, 원, 실패용 격자)의 점 가운데 손끝이 도달 범위 밖인 점은 건너뛴다. 범위는 `check.tool_reach_mm`(팔 원점 기준, 그리퍼별: 단동식 60~255mm, 병렬 75~250mm, 1절)이다. REQ-023 계산(손끝 55mm, 수직 아래, yaw 90에서 약 50~265mm)에 양쪽 10mm 여유를 둔 값이다. 판단은 센서 점을 손끝 점으로 바꾼 뒤 `check.py`가 한다(8.2절, 팔 모듈 import 없음). 메아리 구간이 잘린 끝에 닿으면 그 직선은 중심이 치우칠 수 있어 신뢰도를 0.2 낮춘다. 그래도 `follow_path`가 경로 중간에서 멈추면(IK 실패) 그때까지의 샘플만 쓴다.
  - 근거(기획 초기 계산, 물체 1개, 레이더 오차 σ 25mm. 초음파 세션 계산으로도 물체 1개에서 구간째 건너뜀 57% → 점만 건너뜀 96%로 같은 방향): 직선 ±90mm에 자르기를 쓰면 반경 100~200mm에서 83~93%, 200~240mm에서 77~89%다. 직선을 ±60mm로 줄이면 62~93%로 더 나빴다. 100mm 막대는 빔 번짐까지 ±70mm가 필요해 양 끝을 못 보기 때문이다.
  - 시연 배치는 반경 120~220mm, 물체 중심 사이 120mm 이상, **물체 모서리(가장 가까운 두 변) 사이 80mm 이상**을 권장한다(2026-11-15). 중심 간격만으로는 길이 100mm 물체가 긴 축을 마주 보면 모서리 간격이 20mm까지 내려가고, 센서 높이 154.5mm에서는 빔이 이웃을 합쳐 본다. 근거: 벤치마크 `--scenario pair --pair-gap N`(씨앗 40, #379, 초음파 세션 값) 모서리 간격 10/20/30/40/50/60/80mm에서 성공 낙관 40/51/55/65/88/89/96%, 비관 46/48/52/56/51/49/86%. 낙관은 50mm, 비관은 80mm부터 따로 보인다. B1(빔 반경) 실측 뒤 다시 정하고, I1과 시연 배치는 이 조건으로 놓는다. 고정 시나리오 `demo`·`spread*`의 정의(중심 간격)는 위 표와 맞물려 있어 그대로 두고, 모서리 간격 조건을 넣은 변형은 `demo80`으로 쟀다(#384, 1절 표).
  - 그 밖도 집기는 하지만 확인 성공률이 낮다(8.5절 벤치마크 `single` 반경 220mm 이상, `spread90` 비관에서 약함).
- **첫 점 당기기**(U16 안 A, 2026-11-15 사용자 승인. CHECK에만 쓴다): `tool_reach_mm`으로 자른 뒤에도 경계 근처 점은 IK가 안 풀릴 수 있다. `follow_path`는 한 점이라도 안 풀리면 움직이지 않고 `ik_fail`로 끝나므로, 그 단계 전체를 잃는다(1절 병렬 표의 두 열 차이).
  - 작업 실행이 `follow_path` 결과의 상태를 `probe.feed(poses, status)`로 넘긴다(8.2절). 상태가 `ik_fail`이고 샘플이 비었으면 `Probe`는 그 단계를 버리지 않고, **그 단계 경로의 첫 점을 첫 구간을 따라 둘째 점 쪽으로 `check.retry_pull_mm`(2mm)씩 당긴 경로**를 다음 `next_segment()`로 다시 낸다.
  - 당기는 거리의 합은 `check.retry_pull_max_mm`(20mm)까지다(단계마다 최대 10번). 첫 구간의 남은 길이가 5mm 아래로 내려가면 그만둔다(너무 짧은 첫 구간을 만들지 않는다). 그래도 `ik_fail`이면 지금처럼 그 단계를 unreachable로 건너뛰고 신뢰도를 0.2 낮춘다. 끝 점은 당기지 않는다(끝 점 때문에 남는 `ik_fail`이 벤치마크에서 보이면 U9에서 따로 본다).
  - 다시 부르는 것은 `ik_fail`뿐이다. `out_of_bounds`(안전 검사)·`plan_too_slow`·`stopped`·fault는 다시 부르지 않는다.
  - 실패한 호출은 팔이 움직이기 전에 끝나므로 팔 동작 시간은 늘지 않는다. 늘어나는 것은 계획 계산 시간(단계마다 최대 10번)이고, 구현 PR에서 한 번의 실패 호출이 걸리는 시간을 재서 적는다. 당긴 만큼 그 직선의 시작이 짧아지므로 메아리 구간이 잘린 끝에 닿으면 기존 규칙대로 신뢰도를 0.2 낮춘다.
  - 기록: 당긴 단계 이름과 거리(mm)를 `checks/NNN.json`의 `info`에 남기고, `US-CHECK` 이벤트에 당긴 횟수를 넣는다.
  - `retry_pull_max_mm: 0`이면 끈다(지금 동작).
  - **벤치마크**: `--trim-start`(가상 팔 쪽에서 1mm씩 당기던 것)는 없앤다. 실제 기구학 모드(`--reach kin`)의 가상 팔이 실제 팔처럼 `ik_fail`을 돌려주고, 당기기는 위의 실제 `Probe` 코드가 한다(결정 0037: 같은 코드). 반경 도달 모델에서는 `ik_fail`이 없어 해당 없다. 구현 뒤 병렬 `single`·`demo`·`demo80`을 75~250으로 다시 재서 1절 병렬 표를 한 열로 바꾼다.
- **실패**: L1·L2 모두 메아리가 없으면 후보 둘레 100×100mm를 20mm 격자로 한 번 훑는다. 그래도 없으면 후보를 지우고 `DECIDE`로 돌아간다(레이더 오검출). 같은 자리가 두 번 실패하면 그 사이클에서 다시 고르지 않는다.
- **안전**: 모든 이동은 기존 안전 검사(관절 한계, 작업 영역, 바닥, 결정 0015·0031)를 거친다. 확인 높이가 물체 높이 + 15mm보다 낮아지는 설정은 거부한다. E-STOP·정지는 그대로 동작하고, 확인 중 정지면 ESP32에 `stop`을 보낸다.

## 7. ESP32 ↔ PC 통신 규약 (`system-architecture.md` 6절 대체)
- USB 시리얼 921600bps(보드가 안 되면 115200), 한 줄에 JSON 하나. 측정 줄은 짧은 키로 40바이트 안팎.
- ESP32는 측정마다 자기 시계(µs)를 붙인다. PC는 연결할 때와 10초마다 `sync`로 시계 차이를 구해 PC 단조 시계로 바꾼다(왕복 시간의 절반을 빼는 방식). 목표 오차 2ms 이하(팔 100mm/s에서 0.2mm).
- 측정 간격: 어느 센서든 앞 측정과 33ms(`ping_gap_ms`) 이상 띄운다. 두 센서가 다 켜져 있으면 팔 센서가 우선이고, 팔 센서가 측정하는 동안 레이더는 멈춘다.

| 방향 | 메시지 | 뜻 |
|---|---|---|
| PC → | `{"cmd":"hello"}` | 펌웨어 버전, 센서·서보 종류 묻기 |
| PC → | `{"cmd":"sync","pc":<ns>}` | 시계 맞추기 |
| PC → | `{"cmd":"sweep","from":10,"to":170,"step":4,"bounce":true,"sweeps":N,"max_mm":600}` | 레이더 회전. N=0이면 `stop`까지 계속 |
| PC → | `{"cmd":"stream","hz":30,"max_mm":300}` | 팔 센서 연속 측정 시작 |
| PC → | `{"cmd":"stop"}` | 회전·연속 측정 멈춤. 서보는 그 각도 유지 |
| PC → | `{"cmd":"servo","deg":90}` | 서보 각도(대기 자세) |
| PC → | `{"cmd":"driver","name":"pwm"\|"dxl"}` | 서보 구동 고르기(`servo.driver`, 연결할 때 PC가 보냄). 응답은 `hello`(servo가 바뀐 값). 펌웨어는 켤 때 항상 pwm이다 |
| PC → | `{"cmd":"once","k":"r"\|"a"\|"ra","n":5,"max_mm":600}` | 한 자리에서 n회(실측용). "ra"는 레이더·팔 센서를 번갈아. 끝나면 `done` |
| PC → | `{"cmd":"gap","ms":33}` | 측정 간격(`ping_gap_ms`) 바꾸기(실측 B3용). 응답 `gap` |
| ← ESP32 | `{"t":"hello","fw":"0.3","servo":"pwm"\|"dxl","k":["r","a"]}` | |
| ← ESP32 | `{"t":"sync","pc":<ns>,"us":<µs>}` | |
| ← ESP32 | `{"t":"r","a":86,"d":312,"us":<µs>}` | 레이더 측정. a = 명령 각도(°), d = mm, 응답 없음은 `null`. dxl이면 선택 필드 `"ang":85.7`(측정 직전에 OpenRB가 알려 준 실제 각도, 0.5초 안에 못 받으면 생략). 하위 호환: `ang`가 없으면 `a`를 그대로 쓴다 |
| ← ESP32 | `{"t":"a","d":104,"us":<µs>}` | 팔 센서 측정 |
| ← ESP32 | `{"t":"end","dir":1,"us":<µs>}` | 한 방향 회전 끝 (dir 1 = 증가, −1 = 감소) |
| ← ESP32 | `{"t":"done"}` | `once` 끝 |
| ← ESP32 | `{"t":"gap","ms":33}` | 바뀐 측정 간격 |
| ← ESP32 | `{"t":"err","msg":"..."}` | 오류 |

- **ESP32 ↔ OpenRB 줄 규약** (UART2 115200, ASCII 한 줄): ESP32 → OpenRB `g <deg×10>`(목표 각도, 0~1800 = 0.0~180.0°, 90° = 정면), OpenRB → ESP32 `p <deg×10>`(읽은 실제 각도, 약 5ms마다), 오류 `e 1`(XL330 ping 실패)·`e 2`(읽기 응답 없음). ESP32는 `e` 줄을 PC에 `err`로 올린다. 영점 눈금(서보 90° = 2048)과 방향은 OpenRB 펌웨어 상수(`ZERO_TICKS`, `DIR`)이며 조립 뒤 B4에서 맞춘다.
- 연결이 1초 넘게 끊기면 `UltrasonicSource`는 오류를 내고 작업 실행은 `FAULT`로 간다(팔 통신 끊김과 같은 처리, 결정 0031). 센서 응답 없음(`null`)은 오류가 아니다.

### 8.2 인터페이스 (`system-architecture.md` 4·5절에 추가)
```python
@dataclass
class PathSegment:                 # 작업대 좌표, 손끝(TCP)은 수직 아래
    points_mm: list[tuple[float, float]]   # 손끝 xy (센서 xy 아님)
    tool_z_mm: float
    speed_mm_s: float                       # 실제 속도 = min(이 값, tool_v_max_mm_s × 속도%)
    yaw_deg: float | None = None            # 경로 동안 고정할 손목 각도. None = 지금 값 유지

@dataclass
class PoseSample:                  # 팔 50Hz 루프의 실제 관절값으로 계산
    t_ns: int                      # PC 단조 시계
    tool_mm: tuple[float, float, float]     # 손끝 위치 (작업대 좌표)
    sensor_mm: tuple[float, float, float]   # 팔 센서 위치 = 손끝 + yaw로 돌린 arm_sensor_offset_mm

class CheckProbe(Protocol):
    def next_segment(self) -> PathSegment | None: ...
    def feed(self, poses: list[PoseSample], status: str = "ok") -> None: ...   # status = follow_path 결과 상태(MotionResult.status). "ik_fail"이고 poses가 비면 첫 점을 당겨 다시 낸다(6절 첫 점 당기기, U16)
    def result(self) -> DetectedObject | None: ...   # None = 물체 없음. height_mm = 확인한 실측 높이(결정 0042, 0 = 모름)

class CheckableSource(PerceptionSource, Protocol):
    def start_check(self, candidate: DetectedObject) -> CheckProbe: ...
    def prefetch(self, arm_links_fn) -> None: ...    # 놓는 동안 레이더 미리 돌리기 (T5)
    def rescan(self) -> ScanResult: ...              # RESCAN (2절): 팔이 대기 자세일 때 4바퀴
    def begin_cycle(self) -> None: ...               # 작업 실행 시작 때 한 번: 지운 자리·실패 수를 비움
    def note_failure(self, x_mm: float, y_mm: float) -> None: ...   # 집기 실패·못 가서 못 잰 자리를 알림
    @property
    def give_up(self) -> bool: ...                   # 실패 수가 check.max_fail_per_run에 닿으면 True
```
작업 실행의 `CHECK`:
```python
probe = source.start_check(cand)
while (seg := probe.next_segment()) is not None:
    poses = arm.follow_path(seg.points_mm, seg.tool_z_mm, seg.speed_mm_s, seg.yaw_deg)   # REQ-023
    probe.feed(poses, arm.last_path.status)   # U16: 상태를 같이 넘긴다
obj = probe.result()
```
- `follow_path` 한 번의 호출은 멈추지 않고 이어서 간다. 꺾이는 점에서 서지 않고(`move_p`처럼 블렌딩), 완전히 서는 것은 처음과 끝에만 한다. 한도는 기존 `tool_v_max_mm_s`·`tool_a_max` 그대로이고 **한도가 우선한다**. 꺾이는 점(L3 끝 → L4 시작 등)과 원에서는 가속 한도를 넘지 않을 만큼 속도를 줄여 지나간다(원은 v²/반지름 ≤ `tool_a_max`). 줄인 속도는 `PoseSample` 시각에 그대로 남으므로 `check.py`는 따로 보정하지 않는다. 8.5절 벤치마크의 가상 팔도 같은 규칙으로 속도를 줄인다. 지금 손끝 위치에서 첫 점까지 옮겨 가는 것도 같은 호출에 넣는다. `check.py`는 다음 선의 시작점을 지금 위치에서 가까운 끝으로 고른다.
- **실패 알림**: 작업 실행은 `PICK`이 실패하면 `source.note_failure(x, y)`를 부른다. 확인에서 물체가 없거나 못 간 경우는 인식 모듈이 스스로 센다. 같은 자리(`merge_mm`/2 안)가 두 번째 실패면 그 작업 실행에서 다시 고르지 않는다. 작업 실행은 `DECIDE` 전에 `source.give_up`이 True면 `DONE`으로 간다. 근거: 8.5절 벤치마크(커밋 c3b47d8)에서 알림을 넣으면 성공은 그대로이고 최대 인식 시간이 217→120초로 줄었다. 상한 3은 성공 -1%p 안에서 비관 꼬리를 더 줄였다(`demo` 비관 90% 85→67초).
- **높이 다시 재기**(결정 0052): 후보의 높이를 모르고 수직으로만 집을 수 있으면(`tilt_ok=False`), 작업 실행이 그 후보를 한 번 더 `CHECK`해 높이를 얻는다. 수직 집기가 `no_object`여도 한 번 더 `CHECK`하고 한 번만 다시 집는다. 두 번째 실패는 위의 `note_failure`로 센다.
- 경로는 손끝 기준이다(2026-11-05 사용자 승인). `check.py`는 센서가 지나갈 선(6절)을 정한 뒤, 경로 동안 고정한 yaw로 돌린 `arm_sensor_offset_mm`을 빼서 손끝 점으로 바꿔 `PathSegment`에 넣는다. 이 변환은 `check.py` 한 곳에서만 한다.
- `probe.feed`는 그 구간 시각 범위의 ESP32 팔 센서 측정을 `PoseSample`과 시각으로 맞춰(선형 보간) 점(x, y, h)으로 바꾼다.
- 인식 모듈은 팔 모듈을 import하지 않는다. 팔 링크 위치는 작업 실행이 `arm_links_fn`으로 넘긴다(의존 방향 `system-architecture.md` 2절 유지). 예외는 검증 도구인 `benchmark.py`(8.5절)뿐이다: 가상 팔이 실제 궤적과 같도록 `arm/trajectory.py`를 읽는다. `radar.py`·`check.py`·`source.py`는 팔을 import하지 않는다.
- 이벤트(`Studio.bus`): `us.sweep`(각도별 값), `us.candidates`, `us.check_path`(구간과 점), `us.check_result`. GUI는 이것으로 그린다(REQ-024).

### 8.5 성능 벤치마크 (결정 0037)
초음파 성능 숫자는 이 벤치마크로만 낸다. 초음파 세션이 만들고 관리한다. 실행은 `python -m so101_studio.perception.ultrasonic.benchmark [--scenario 이름] [--seeds N]`이고, 레이더·확인 코드는 실제 `radar.py`·`check.py`를 그대로 돌린다. 결과는 표로 내고, 커밋과 시나리오 이름을 함께 남긴다(`runs/bench/`). 새 아이디어(확인선 길이, 모드, 속도 등)는 이 벤치마크의 옵션으로 붙인다.

| 항목 | 값 (기획이 정함, 실측으로 고침) |
|---|---|
| 손목 센서 빔 반각 | 비관 15°, 낙관 7.5° (B1로 고침) |
| 레이더 면 반사 허용각 | 비관 8°, 낙관 12° (B2로 고침). 허용각 밖의 비스듬한 면은 메아리 없음 |
| 레이더 모서리 반사 | 빔 반각의 0.7배 안, 거리 비관 300mm·낙관 450mm까지, 확률 비관 0.5·낙관 0.9 |
| 거리 잡음·응답 없음 | 2mm + 거리의 0.3%, 응답 없음 3% |
| 레이더 서보 지연 | 갈 때·올 때 ±3° (B4로 고침) |
| 팔 | 실제 팔 궤적 코드(`arm/trajectory.py`의 `fillet_path`·`LookaheadShape`)를 그대로 쓴다: 속도 100mm/s, 접선·구심 가속 `tool_a_max`/√2, 모서리 2.5mm, 180° 되돌아감에서 정지. 호출 사이 0.25초, 손끝 도달 50~265mm(REQ-023 계산). `--sim` 실측 경로 시간과 ±0.05초 안 (시험 `test_fake_arm_matches_real_arm_times`) |
| 대기 자세 | `config/robot.yaml`의 `poses.radar_clear`를 그대로 읽는다(결정 0041, 위로 세운 자세). 대기 자세에서 확인 높이까지 내려오는 이동도 인식 시간에 넣는다 |
| 물체 | 30×100, 40×80, 50×50mm, 높이 40mm, 방향 0/45/90/135° ±5° |
| 배치 시나리오 | `spread90`: 3개, 반경 100~240mm, 방위 25~155°, 중심 간격 90mm 이상. `spread120`: 같은 범위에 간격 120mm 이상. `demo`: 반경 120~220mm, 간격 120mm 이상. `single`: 1개, 반경 100~240mm 구간별. 씨앗값 고정, 시나리오마다 20개 이상 |
| 판정 | 팔이 집으러 간 자리(확인 결과)에 가장 가까운 실제 물체가 30mm 안이면 그 물체를 집은 것으로 본다. 위치 오차 15mm 이하이고 방향까지 맞으면 성공(정사각형은 위치만). 레이더 후보와 다른 물체를 정확히 잡아도 성공이다(실제로도 그 물체를 집는다) |
| 내는 값 | 물체 3개 중 성공 수 평균, 인식 시간 평균·90%(레이더 + 확인, 집기·놓기 제외), 물체 1개 반경 구간별 성공률, 비관·낙관 각각 |

1절의 합격 기준(실물)은 그대로 두고, "기획 초기 계산" 칸은 이 벤치마크 결과가 나오면 바꾼다.

### 8.4 기록
- `runs/<시각>/scans/NNN.json`: 레이더 바퀴별 원자료, 기준값, 호, 후보, 지운 각도.
- `runs/<시각>/checks/NNN.json`: 구간, `PoseSample`, 팔 센서 측정, 점(x, y, h), 결과와 신뢰도.
- `events.jsonl`(결정 0030 공통 머리): `US-CONNECT`, `US-LOST`, `US-BASELINE`, `US-CANDIDATES`, `US-CHECK`(결과·소요 시간), `US-CHECK-FAIL`.
- `summary.json`에 물체별 레이더·확인 시간을 넣어 비교 실험(인식 속도)에 쓴다.

## 11. 정할 것과 열린 질문
- 스캔 서보는 OpenRB-150 + XL330(결정 0043)이다. 서보 전원은 5V(A 충전기 또는 B 강압 모듈, 결정 0043-2)이고 12V를 OpenRB VIN에 넣지 않는다. 손목 브래킷은 결정 0063이다(0035는 대체됨).
- `check.tool_reach_mm`은 그리퍼별로 정했다(1절: 단동식 60~255, 병렬 75~250, 2026-11-15). 병렬 값은 팔 세션 도달 계산(날값 73~250, #393)과 대조했고 실물 A0 뒤 다시 정한다.
- 모드는 하나로 정했다(결정 0038). T8은 옵션이다.
- 초음파 세션은 결정 0036으로 만든다(Sonnet, 폴더 `../so101-studio-us`).
- 도달 범위는 6절 "도달 범위로 자르기"로 정했다(U3 결과). 실물에서 바깥쪽이 더 모자라면 센서를 손끝 바깥쪽에 다는 브래킷(센서 도달 최대 약 30mm 증가, 턱 간섭 확인 필요)을 검토한다.
- 레이더 시야에 팔 받침이 들어오는 영향은 기준값에 포함된다고 보고, R1에서 확인한다.
