# 0048. 설계서 점검에 EGM 플러그인을 좁게 쓴다: 구현 전 Stage 9 리뷰와 설계서-코드 어긋남 보고

상태: 확정 · 2026-11-07 (사용자 승인으로 합침). 실행 방식은 대체됨(→ 0056, 총괄이 하위 에이전트로). 0045·0046(코드 테스트·리뷰)은 바꾸지 않고, 설계서 쪽 점검을 더한다.

## 맥락
- Google이 공개한 Elephant-Goldfish Model(EGM)은 플러그인이다(github.com/google/elephant-goldfish-model, Apache-2.0, 시험 때 0.1.1). 설계서는 맥락을 가진 세션이 쓰고, 맥락 없는 새 하위 에이전트("금붕어")가 그 문서와 문서가 가리키는 코드만 보고 빈틈을 찾는다.
- 2026-11-07에 별도 세션에서 gui-spec 12절을 Stage 9(Implementation Readiness)로 시험했다. 결과는 다음과 같다.
  - 지적 8건이 모두 실제로 있는 어긋남이었고, gui-spec 12절 보완과 결정 0047로 반영했다.
  - 다만 리뷰어는 main만 보므로, 합쳐지지 않은 PR(#41)에 이미 있는 답을 "미정"으로 올렸다.
  - 리뷰어는 메인 세션과 같은 모델로 돌아 사용량이 크다.
- 우리 쪽 실수 가운데 문서를 쓴 쪽이 맥락 때문에 못 보는 것들이 있었다: 결정 0039의 닿을 수 없는 자세, `ignore_zones`를 넘기는 곳이 없던 버그.

## 결정
1. **설치**: 각 PC에 사용자 범위로 설치한다(`claude plugin marketplace add google/elephant-goldfish-model`, `claude plugin install egm@egm`). Claude Code 2.1.271 이상이어야 한다.
2. **쓰는 것 1 — 구현 전 점검**: 설계서의 새 절이나 큰 개정을 구현하기 전에 총괄이 `/egm:egm-review <설계서>`를 "Implementation plan only"(Stage 9)로 돌린다.
   - 대상 범위(절)와 GoldfishContext(관련 결정, 해당 코드 폴더)를 지정한다. 결과는 꼭 고칠 것 / 있으면 좋은 것 / 틀린 지적으로 나눠, 꼭 고칠 것만 [기획 요청]으로 올린다.
   - 실행은 작업 중인 세션이 아니라 **새로 연 짧은 세션**에서 한다(작업 세션의 맥락과 사용량을 아끼려고).
   - 합쳐지지 않은 관련 PR이 있으면 그 브랜치를 GoldfishContext에 넣는다.
3. **쓰는 것 2 — 설계서-코드 어긋남**: 큰 합치기가 몰린 날 마칠 때, 그날 구현한 설계서 하나를 대상으로 `/egm:egm-drift-report`를 돌린다. 전체 테스트(0046-2)와 같은 때다. 어긋남은 [기획 요청]으로 올리고, 문서를 고칠지 코드를 고칠지는 사용자가 정한다.
4. **쓰지 않는 것**:
   - brainstorm·draft·resolve: 기획 세션·superpowers·`/grill-me`와 겹친다.
   - bootstrap: 폴더마다 README를 만들어 문서 규칙(네 위치)과 맞지 않는다.
   - 5단계 전체 리뷰: 사용량에 비해 이득이 작다.
5. **산출물**: `runs/egm/`(git 제외)에 둔다. 커밋하지 않는다(문서 규칙의 중간 산출물). CLAUDE.md에 `EGM artifact directory: runs/egm` 줄을 둔다.
6. **기억 유지와의 관계**: 이어 가기 위한 기억은 지금처럼 `project-status.md`, `work-queue.md`, 요청 대장, 결정 기록에만 둔다. EGM은 그 문서들이 코드와 어긋났는지 찾는 도구일 뿐, 따로 기억 문서를 만들지 않는다.
7. **코드 쪽은 그대로**: 코드 PR의 테스트·리뷰는 0045·0046(관련 테스트, `code-review`, ruff 훅, Playwright)을 따른다. EGM은 설계서만 본다.
