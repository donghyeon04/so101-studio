# 0026. GUI의 E-STOP은 별도 감시 프로세스가 지킨다

상태: 확정 · 2026-11-02

## 맥락
GUI 세션의 기획 요청(3번): `backend.estop()`이 웹 서버와 같은 프로세스에 있어 서버가 멈추면 E-STOP도 같이 멈춘다. 안 셋(설계 유지 / 별도 감시 프로세스 / 같은 프로세스의 감시 스레드)의 장단점을 비교한 뒤 사용자가 별도 감시 프로세스를 골랐다. 레퍼런스는 PIPER Studio의 `estopd`다(웹 서버와 분리된 프로세스, 브라우저 heartbeat가 끊기면 로봇 제어 프로세스를 멈춤).

## 결정
- 감시 프로세스 `python -m so101_studio.watchdog`을 GUI와 따로 띄운다. GUI가 시작할 때 함께 띄우고, 감시 프로세스가 없으면 실제 팔을 움직이지 않는다.
- 감시 프로세스는 heartbeat 두 개를 받는다. 조작권을 가진 브라우저가 감시 프로세스에 직접 보내는 것과, GUI 서버의 이벤트 루프가 보내는 것이다. 실제 팔이 연결된 동안 둘 중 하나라도 1초 넘게 끊기면 멈춘다.
- 멈추는 순서는 두 단계다. ① 팔 프로세스 안의 정지 수신 스레드에 정지 명령을 보낸다(토크는 유지한 채 그 자리에 섬, `ctl.estop()`). ② 0.3초 안에 응답이 없으면 팔 프로세스(`ArmService`가 들어 있는 GUI 프로세스)를 종료한다. 명령이 끊기면 서보는 마지막 목표 자리에 선다.
- 감시 프로세스는 키보드 단축키(전역 키 읽기, `keys`와 같은 방식)로도 E-STOP을 받는다. GUI 화면이 멈춰도 쓸 수 있다.
- 감시 프로세스와 정지 수신 스레드는 팔 세션이 만든다(REQ-009). heartbeat 보내기, 감시 프로세스 띄우기, 상태 표시는 GUI 세션이 만든다. 시뮬레이션에서는 멈추지 않고 기록만 한다.
- 소프트웨어 E-STOP은 마지막 안전장치가 아니다. 실제 팔을 쓸 때는 전원 스위치 옆에서 지켜보는 규칙을 유지한다.
